# Barcode / QR Labels and Scanning — Recon Report

**Mode:** read-only recon. No code, packages or other files were changed.
**Scope:** `backend/` (ASP.NET Core, EF Core/PostgreSQL) and `frontend/` (React + MUI).
**Date:** 2026-10-28

---

## Executive summary

- **The codes on the main v1 entities are suitable for labels.** Sample, Media lot, Cryovial, Solution Preparation (MP/DL/VS/WS), HPLC Run and SST codes are system-generated. Each has a database unique index and is never edited after it is issued.
- **Material Stock lots and Equipment are not yet suitable.** A Material lot has no unique code of its own: `BatchNumber` and `Code` both repeat across lots. Both equipment codes can be edited, and the main `Equipment.Code` is not unique in the database. Labels for these need a decision first (Gaps G1–G3).
- **No barcode, label or print-audit code exists yet.** There is no barcode package in `package.json` or any `.csproj`. Printing today is browser `window.print()` on HTML views, plus a dependency-free server-side PDF writer (`PdfCanvas`).
- **A global search already exists** (`Ctrl+K`, `GlobalSearchDialog` → `GET /api/search/global`) and is filtered by section. It is the natural place for "scan to open". It needs an exact-match lookup and a fix for a race between Enter and the 300 ms debounce, which a keyboard-wedge scanner will hit (Gap G7).
- **Recommended v1:** 2D Data Matrix (or QR) that encodes `TYPE:CODE`, with the code also printed as text. Labels render on the server as vector PDFs sized to the label stock, by extending `PdfCanvas`. A backend scan-lookup endpoint applies the existing section rules. `LABEL_PRINTED` / `LABEL_REPRINTED` audit events use `AuditEventService`, and a reprint requires a reason.

**Notes on A**

- The prompt's "`MP-[Method] [Seq]/[MMYYYY]`" and "`DL-[Seq]/[MMYYYY]`" are out of date. The current format has an extra `/`: `nn/MM/yyyy` (`SolutionPreparationCode.cs:66`). SST and Run codes use `nn/MMyyyy` (`SystemSuitabilityRunCode.cs:76`).
- Every sequence-based generator uses "highest issued + 1", backed by a unique index and one retry, except Samples. Samples use "count this month + 1" (`ReferenceNumberGenerator.cs:51-54`), which the unique index still protects. Samples are cancelled or voided (`SampleStatus` Cancelled = 7, Voided = 8), never deleted, so the count does not reuse numbers.
- Dates in codes use the lab clock (`ILabClock`, Africa/Cairo). Dates printed on labels must use the same clock.

## D. Audit and control

- **Printing is not audited today.** No `PRINT` action code exists. The closest precedents:
  - `AuditEventService.RecordUserEventAsync` (`Application/Services/AuditEventService.cs:21-60`) writes an immutable `AuditLog` row with an `EVT-nnnnnnn` UID, `ActionCode`, `AuditActionCategory`, `EntityName`/`EntityId`, `Reason`, `SourceContext` and an optional `SampleId`, so it shows in Audit Search by sample. **This is the pattern to reuse.**
  - `AccessReviewService.cs:368` records `ACCESS_REVIEW_EXPORTED` under `AuditActionCategory.ImportExport`, a precedent for auditing a read-only output.
  - `DataExportLog` / `DataExportAuditService` (`Domain/Entities/DataExportLog.cs`, `Application/Services/DataExportAuditService.cs`) is a separate log for CSV exports. It is not a good fit because it has no entity link and no reason.
  - Normal create/update/delete changes are captured automatically by `MicroLimsDbContext.SaveChanges` → `AuditLog`, so a lot selected by scan is already audited through the write it triggers.
- **Recommendation:** audit every label print as `LABEL_PRINTED` and every reprint as `LABEL_REPRINTED`. Record who, when (lab and UTC), entity type, ID and code, template, copies, and **a required reason for reprints**. `AuditActionCategory` (`Domain/Enums/AuditActionCategory.cs`) has `Other = 9` and `ImportExport = 8`. A new `Labelling` value can be added at the end because the enum is stored as an int. A print counter, or a "first print vs reprint" check based on the existing audit rows, decides which event applies. **Do not audit individual scans.** They are reads, and the action that follows is audited already. An e-signature for reprints is optional (Q8).
- **Status handling, so a scan never selects an unusable record:**

| Entity | Status fields | Suggested scan behaviour |
|---|---|---|
| Sample | `SampleStatus` (… Approved, Rejected, RetestRequested, **Cancelled = 7, Voided = 8**) | Opening is always allowed (read-only view with a status banner) |
| Media lot | `MediaStatus` Prepared/Active/Expired/QuarantineFailed/Destroyed/OutOfStock, plus `ApprovalStatus` and `IsReleasedForUse` (`Media.cs:43-56`) | Select only if released and in date. The dropdown lists are already filtered, and the server re-checks. |
| Solution preparation | InProgress/Prepared/Expired/Discarded/Cancelled. Expiry is computed by `SolutionPreparationResponse.EffectiveStatusOf` | Select only if effectively Prepared (already enforced, `HplcRunService.cs:335`) |
| SST / HPLC Run | `HplcSstStatus` Pending/Passed/Failed; `HplcRunStatus` Open/Completed/Abandoned | Opening allowed |
| Material lot | Computed `StockStatus` Expired/Depleted, not stored (`Material.cs:84-91`) | Select only if `IsUsable` |
| Cryovial | `ApprovalGateStatus`, `VialsRemaining` | Select only if approved and vials remain |
| Equipment Inventory | InService/OutOfService/**Retired** | Select only if InService |
| Equipment (master) | **No status field at all** | Cannot be blocked today (G2) |
| Column | `IsActive` | Select only if active |

  Principle (CLAUDE.md, "Laboratory Logic on Backend"): the frontend should never block a scan by itself. The lookup endpoint returns `usable` and `blockedReason`, and the existing service validation stays the final gate.

## E. Permissions and department scoping

- **The permission catalogue** is `backend/MicroLIMS.Shared/Constants/PermissionConstants.cs`, seeded by `Persistence/Seed/DbSeeder.cs` and resolved dynamically by `API/Authorization/PermissionPolicyProvider.cs`. Relevant codes today: `Samples.Receive` (`:16`), `Samples.ReceiveOwnLab` (`:104`), `Cryovials.Manage` (`:21`), `Materials.Manage` (`:23`), `Equipment.Manage` (`:25`), `Media.Prepare` (`:100`), `Solutions.Prepare` (`:110`), `Hplc.Operate` (`:115`).
- **Recommendation:** the **first print** is allowed to whoever holds the create permission for that entity (receiver, media preparer, solution preparer, and so on), so labels can print as part of creation. **Reprinting** needs a new **`Labels.Reprint`** permission, given to section heads and supervisors by default. Optionally add `Labels.Print` if Mohamed wants printing separated from creating. Each new code needs a seed row and role mapping in `DbSeeder`.
- **Department (section) scoping is enforced on the backend:**
  - `IUserSectionScopeService` (`Application/Interfaces/IUserSectionScopeService.cs`). Read scope: `GetReadableSectionIdsAsync` (null means all sections, for `Sections.ViewAll`). Per-record guards: `EnsureSampleAccessAsync`, `EnsureMediaAccessAsync`, `EnsureCryovialAccessAsync`, `EnsureMaterialAccessAsync`, `EnsureEquipmentAccessAsync`, `EnsureEquipmentInventoryAccessAsync`, `EnsureColumnAccessAsync`, all with `SectionAccess.Read`. Writes always follow membership.
  - Examples: `MediaController.cs:116,125` calls `EnsureMediaAccessAsync(..., SectionAccess.Read)` before returning a summary or PDF.
  - Global search applies read scope for each entity (`GlobalSearchService.cs:36,40`): samples through test-order and sign-off sections (`:139-140`), materials (`:244`), equipment inventory (`:286`), media through `Material.SectionId` (`:329`), solution preparations (`:418`).
  - Section ownership: Sample through `TestOrder.SectionId`; Media and Cryovial through their source `Material.SectionId`; Solution preparation, HPLC run, Equipment, Material and Column through their own `SectionId`.
  - **Requirement:** the scan-lookup endpoint must run the matching `Ensure*AccessAsync(Read)` guard, or an equivalent scope filter, and return "not found" for out-of-scope records so it does not reveal that they exist. `GlobalSearchController` has only `[Authorize]` and relies on section filtering, which is enough for opening. Selecting is re-checked by the write endpoints.

## Answers to the report questions

### 1. Symbology
| Use | Recommendation | Why |
|---|---|---|
| Sample bottles / bags (codes like `FP1026001`, 9–10 characters, letters and digits only) | **Code 128** is fine (about 40 mm wide at a 0.25 mm module), or Data Matrix | Works with any 1D scanner. Code 128 subset C packs the digit run. |
| Petri plates, tubes, cryovials, small flasks; any code ≥15 characters (MP ≤34, SST ≤34, Cryovial with no length limit) | **Data Matrix** (ECC200) | A 34-character Code 128 is about 110 mm wide at 0.25 mm, too wide for tubes or plates. Data Matrix fits it in about 24×24 modules (≈7 mm square). It is the GS1 healthcare standard for small items. |
| Tablet camera scanning | **QR** | Phone and tablet decoders read QR most reliably. Data Matrix also works but is less robust on webcams. |

**Recommendation:** choose **one 2D symbology (Data Matrix) for all labels** and buy 2D imager scanners, which also read 1D. Use Code 128 only if the lab must keep 1D-only scanners, and then only for Samples and Equipment, whose codes are short.

### 2. Barcode content
| Option | Pros | Cons |
|---|---|---|
| Record code only (`TSA/03/26`) | Human-checkable. Works in today's search boxes with no change. | Ambiguous across types: an `MP-…` code is clear, but a product code could look like a lot. Contains spaces and `/`. Unusable for Material lots and Equipment (not unique or immutable). |
| `TYPE:ID` (database id) | Short, immutable, unambiguous. Survives code renames (Equipment). | Not human-checkable. Database IDs differ between environments (a restored test database maps scans to different records). Typed into a normal text field it means nothing. Exposes internal IDs. |
| **`TYPE:CODE`** (e.g. `S:FP1026001`, `MED:TSA/03/26`, `SP:MP-VIT-C 05/11/2026`, `SST:VIT-C S.S 05/112026`) | Unambiguous for one global scan box. The code part can be checked by eye against the printed text. Stable across environments. The resolver can also accept bare codes as a fallback. | Needs a type registry. Only valid for entities with unique, immutable codes (rows 1–8 in section A). |

**Recommendation:** use `TYPE:CODE` for v1 entities. For Material lots and Equipment, first add an immutable unique label identifier (G1/G2), then use `TYPE:LABELID`. Short type prefixes reduce exposure to the keyboard-layout risk in G6.

### 3. Rendering approach
| Approach | Validation | Printer independence | Fit here |
|---|---|---|---|
| **Server-side vector PDF** (extend `PdfCanvas`) | One rendering path, easy to test (golden-file PDF tests). Barcodes are drawn as filled rectangles, so they print sharp at any DPI. The Code 128 encoder is small enough to own. A Data Matrix or QR encoder needs Reed-Solomon: either write and validate one, or **qualify one small MIT library** (ZXing.Net, or QRCoder for QR only) used only for the module matrix, while `PdfCanvas` does the drawing. | Any printer that prints PDF at 100% scale, both A4 sticker sheets and thermal printers through their driver. | **Recommended.** Matches the existing `*/pdf` endpoints and the dependency policy. `PdfCanvas` needs a configurable page size instead of the A4 constants (`PdfCanvas.cs:40-44`). |
| Client-side (JsBarcode / bwip-js + browser print) | Adds a frontend dependency to qualify. Output depends on the browser's print scaling, margins and "fit to page", which is a known label-misalignment problem. The global A4 `@page` interferes unless a new window is used. | Good in theory, fragile in practice | Possible for previews only |
| Printer language (ZPL for Zebra) | Exact, fast, sharpest on thermal printers. A separate template language to validate. | **Tied to one printer family.** Needs a raw-print path (Zebra Browser Print agent or a server-side print queue) | Add later as a second output **if** Zebra is chosen (Q1) |

### 4. Global scan box vs field-level inputs
Both are needed, at different stages:
- **Scan to open → global.** Reuse the existing `Ctrl+K` `GlobalSearchDialog` in the header (G7 fix plus exact-match lookup). Users already know it, and it is already scoped by section.
- **Scan to select → field-level.** A reusable "scan" adornment or field on pickers that matches against the options already loaded. Start with the shared `MediaLotIncubatorFields` (four screens), then `WizardMobilePhasesStep` and `WizardColumnStep`, then `ComponentLotPicker` and `MediaPreparationDialog` once G1 is solved. A global box cannot know which field to fill.

### 5. Label templates
**v1: fixed templates per entity, in code, chosen by label size** (for example "small 2D" for tube or plate, and "standard" for bottle or flask). The fields come from the entity: code, name or product, prep date, expiry, prepared by, and status at print time. A configurable label designer is a validated-configuration feature of its own (change control, versioning). Defer it until the lab has used the fixed templates.

### 6. Risks
See the next section: G1, G2 (editable or duplicate codes), G6 (characters and keyboard layout), G11 (offline printing).

## Proposed implementation plan (each phase ends with a sign-off gate)

**Phase 0: Decisions (no code).** Mohamed answers the open questions below. Choose the symbology, payload, label sizes and printer.
*Gate:* signed decision record (printer model, label sizes, symbology, v1 entities).

**Phase 1: Label generation.**
- Backend: `ILabelRenderer` (Application abstraction) and an Infrastructure implementation that extends `PdfCanvas` with custom page sizes and barcode drawing (filled rectangles). Code 128 encoder, plus the Data Matrix decision (own encoder or a qualified library).
- `GET /api/labels/{entityType}/{id}/pdf?template=…&copies=…`, which applies the `Ensure*Access` guards.
- Fixed templates for Sample, Media lot and Solution Preparation.
- Tests: encoder test vectors, decode round-trip of the rendered PDF in tests, golden layout tests.
*Gate:* test print on the real printer and stock. Scan readback rate of 100% on N samples with the real scanners. Template content approved.

**Phase 2: Print and audit.**
- `LABEL_PRINTED` / `LABEL_REPRINTED` through `AuditEventService` (with reason, copies and template). Add the `Labels.Reprint` permission and its seed.
- "Print label" buttons: on Media lot and Solution Preparation records, and after sample receipt (G14). Reprint dialog that requires a reason.
*Gate:* QA reviews the audit trail entries in Audit Search, the permission matrix and the SOP draft for label handling.

**Phase 3: Scan to open.**
- `GET /api/scan/resolve?value=` → `{entityType, id, code, status, usable, blockedReason, navigationTarget}`. Exact match on `TYPE:CODE` or a bare code. Section-scoped. Out-of-scope records return "not found".
- Fix the Enter race in `GlobalSearchDialog` (G7). Add runs, SST records and cryovials to the lookup.
*Gate:* a cross-section test, where a user in section A scans a label from section B and gets "not found". Tested with the real scanners and keyboard layout (G6).

**Phase 4: Scan to select in workspaces and preparation screens.**
- A reusable scan field. Order: `MediaLotIncubatorFields` → HPLC mobile-phase and column steps → (after G1/G2) `ComponentLotPicker`, `MediaPreparationDialog`, equipment pickers.
- Add the immutable stock-label ID for Material lots (migration) and tighten equipment code uniqueness (G1/G2), then add Material, Cryovial and Equipment label templates.
*Gate:* a usability walkthrough with analysts. Confirm the server still rejects unusable lots chosen by scan. Regression tests on the affected panels.

## Open questions for Mohamed (decision-ready)

1. **Printer:** a thermal label printer (which model, for example Zebra ZD421 at 203 or 300 dpi) or A4 sticker sheets (which product, for example Avery L7651) on the existing office printers? This decides whether ZPL is ever needed.
2. **Label sizes:** sample bottle, Petri plate (lid or base), tube or cryovial, media bottle, solution flask. Give mm sizes, or the label-stock product code for each.
3. **Label content per entity:** beyond the barcode, which of these fields: code, name or product, prep date, expiry, prepared by, storage condition, status at print? Arabic text needed? (The PDF writer currently uses Helvetica, which is Latin only.)
4. **Scanners:** USB keyboard-wedge 1D, 2D imagers, or tablet cameras? Is an Arabic keyboard layout ever active on lab workstations (G6)?
5. **v1 entities:** confirm Sample, Media lot and Solution Preparation (recommended). Cryovial, Material lot and Equipment follow in phase 4.
6. **Symbology:** approve Data Matrix for everything (needs 2D scanners), or Code 128 for Samples and Equipment plus Data Matrix for small items?
7. **Payload:** approve `TYPE:CODE`, with bare codes also accepted by the resolver?
8. **Reprint control:** is a reason enough, or is an e-signature (password re-entry) also needed? Who may reprint: section heads only, or also analysts?
9. **Equipment labels:** which register's code goes on the physical sticker, workflow `Equipment` (e.g. `INC-002`) or asset `EquipmentInventory` (e.g. `INC-F-ML-F-01-003`)? May codes be frozen once labelled?
10. **Material lots:** approve adding a system-generated stock-label ID (e.g. `STK-2026-00123`) printed at goods receipt?
11. **Auto-print:** should labels print automatically when a record is created (receipt or preparation complete), or only on demand?
12. **Barcode library policy:** may we qualify one small open-source 2D encoder (ZXing.Net or QRCoder, MIT), or must it be written in-house like `PdfCanvas`?
