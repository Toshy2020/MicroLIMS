## Current state of `HplcAssayResult` / HPLC Assay, as built

`HplcAssayResult` (`backend/MicroLIMS.Domain/Entities/HplcAssayResult.cs`) is a single flat entity, one row per
`TestOrder`: `Id`, `TestOrderId`, `SystemSuitabilityRunId`, standard snapshot (`StandardPurityPercent`,
`StandardWeightMg`, `StandardDilution`, `StandardMeanArea`), sample inputs (`SampleWeightMg`, `SampleDilution`),
`ReplicatesJson` (raw injection areas + per-injection %), `MeanAssayPercent`, `ReportedResult`, `AlertLimit` /
`ActionLimit` / `SpecLimit` (text snapshots), `ComparisonStatus`, `IsActive`, signature/audit fields.

Formula, as coded (`TestWorkflowEngine.RecordHplcAssayResultAsync`, ~line 2064; calculation ~2134-2138): per
injection `(Area / StandardMeanArea) × (StandardWeightMg / SampleWeightMg) × (StandardPurityPercent / 100) ×
(SampleDilution / StandardDilution) × 100`. Injections are averaged with equal weight; the mean is rounded to
1 dp AwayFromZero (line 2143) and compared **unrounded** against the limit via `SpecificationEvaluator.Evaluate`
(or a `Compare` fallback) at line 2155. There is **no moisture/dry-basis correction, no separate %LC/label-claim
conversion step, and no `ThWt` constants anywhere** — dilutions are typed explicitly at result entry, and purity
is assumed to already be on a dry (or otherwise final) basis. Any number of injections is accepted (no fixed
replicate count, no preparation stage, no weigh-in window checks). This is exactly what the prompt's Rule 12
says must be replaced, not patched.

## Status of the "shared per-parameter result foundation"

Raised previously in the other-equation-types recon (`docs/FP_Other_Equation_Types_Phase0_Recon.md`, F1/F2, with
titration mentioned in F3/F6/F8/F11) and in the Calibration Curve recon (`docs/FP_Calibration_Curve_Phase0_Recon.md`
F10, "the largest part of the build"). **Status: built**, not partial. Commit `6afa03d` (F0 of that plan) added
`TestAnalysis` (one signed entry per `TestOrder`: `AnalysisType` [`WorkflowType`], `EquipmentId`, `AnalysedAt`,
`UnitAmount`, `SampleMatrix`, `ConditionsJson`, `ValidityRecordType/Id`, signature, `Comment`, `IsActive`),
`ParameterResult` (one row per `TestAnalysis` × `Specification`: `ReportedValue`, `ReportedDisplay`, `Unit`,
`SpecLimit`, `ResultBasis`, `ComparisonStatus`, `OverRange`, `BelowLoq`, `ValidityRecordItemId` → FK
`CalibrationRunAnalyte`, `CalculationJson`, `StageReached`, `IsActive`) and `ResultReading` (`Kind`, `Index`,
`Stage`, `TimePointMinutes`, `Value1-3`, `Text`, `ComputedValue`, `Passed`). Eight equation types already use it:
ElementalAssay, Measurement, GravimetricLoss/Residue, Qualitative, Dissolution, Disintegration, WeightVariation
and — as of 2026-09-21/22 (commits 383fc0a, 1829290, dc71e2a) — `HplcMultiAnalyte`. This answers Q7 with a
verified "built" (see the open-questions list below).

The one gap: `ParameterResult.ValidityRecordItemId` is a typed FK to `CalibrationRunAnalyte` only. `HplcMultiAnalyte`
already works around this by storing its `SystemSuitabilityRunAnalyteId` inside `CalculationJson` instead
(`docs/FP_Multi_Analyte_HPLC_Build_Spec.md` M2, and confirmed at `ParameterResult.cs:32-33`). A generalized
Standard-Comparison Assay would need the same workaround, or a widening of that FK — flagged as a design note,
not an open question, since it doesn't change any SOP constant.

## How large is the HPLC Assay rework, relative to a from-scratch build

Small-to-medium, not a rewrite. The expensive, general-purpose parts already exist and are reused unchanged:
the shared per-parameter result foundation (F5), `TestAnalyte` + `SystemSuitabilityRunAnalyte` for per-analyte
standards and optional SST criteria (F4/F10), the review/projection/summary/CoA generic branches (F2), and the
`decimal`/lab-clock/signature/section-scope conventions used everywhere in FP. What's genuinely new is: the
formula itself (ThWt/MC/P terms replacing dilution ratios — small, isolated), the weigh-in-window gate (F14,
no precedent), `SamplePurpose`/sample-type structure (F6), the titration response mode (F11, greenfield but
narrow), and the AAS equation type (new but can reuse most of the elemental-assay/`CalibrationRun` shape,
lightened per F12). The approval-gate generalization (F3) is a fix that was needed regardless of this rework.
