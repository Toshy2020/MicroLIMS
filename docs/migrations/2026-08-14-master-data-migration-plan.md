## 5. Fields referencing Users — must NOT copy source IDs

None of these columns has a DB-level foreign key to `Users` (Postgres allows the loose
int), but they are used by the application as "who did this" attribution:

| Table | Column | Nullable | Source values seen |
|---|---|---|---|
| Materials | CreatedByUserId | NO | 1 |
| Materials | LastModifiedByUserId | NO | 1, 4, 5, 7 |
| EquipmentInventories | CreatedByUserId | NO | 1 |
| EquipmentInventories | LastModifiedByUserId | NO | 1 |
| Media | PreparedByUserId | NO | 0 (!), 4, 7 |
| Media | ApprovedByUserId | YES | null, 4, 5 |

Source `Media.PreparedByUserId` is frequently `0`, which isn't even a valid source user —
further confirmation that these columns can't be trusted as durable identity and must be
re-pointed rather than copied.

**Decision applied in the script:** every audit/User-reference column above is resolved via
`(SELECT "Id" FROM "Users" WHERE "Username" = 'admin' ...)` in production — i.e. all migrated
rows are attributed to the production admin account, regardless of which dev user originally
touched them. `ApprovedByUserId` stays `NULL` where the source had no approver, and resolves to
admin where the source had *any* approver (we don't try to distinguish which one — see below).

This satisfies "never copy source Users" but does lose per-user attribution (dev users MMA,
MMASH, MMAAN collapse to admin). **If you'd rather preserve real attribution**, the alternative
is: first create Users in Neon with the same `Username` values as the dev DB (MMA, MMASH,
MMAAN), then swap the `'admin'` literal in the script for a per-row username lookup. That's a
straightforward follow-up if wanted — flag it and I'll regenerate.

A pre-flight check (`DO $$ ... RAISE EXCEPTION ...`) at the top of the script aborts
immediately, before any inserts, if production has no `Username = 'admin'` row.

## 6. Identity/sequence behavior

All 14 `Id` columns are `GENERATED BY DEFAULT AS IDENTITY` (i.e. an explicit value can be
supplied on INSERT, unlike `GENERATED ALWAYS`). The script inserts explicit source `Id` values
to preserve the FK graph between the 14 tables, then resets each table's sequence with:

```sql
SELECT setval(pg_get_serial_sequence('"Table"', 'Id'),
              COALESCE((SELECT MAX("Id") FROM "Table"), 1), true);
```

so that the *next* app-generated insert in Neon continues after the highest Id now present
(source or pre-existing production, whichever is higher) rather than colliding.

## 8. Conflict analysis and how the script avoids each class

Since this environment has no Neon credentials, the script can't check live Neon contents.
Instead every INSERT is written to be safe regardless of what's already there:

1. **Id already taken by an unrelated row** → guarded by `WHERE NOT EXISTS (... WHERE "Id" = v.id)`.
   The row is silently skipped, never overwritten.
2. **Business key already present under a different Id** → guarded by a second
   `NOT EXISTS` on the real unique constraint (Organisms name/ATCC, MediaTypes.Class,
   Items/TestDefinitions/EquipmentInventories.Code, Media.LotNumber, the two composite
   uniques). Prevents duplicate business entities and unique-constraint violations.
3. **FK parent resolved by business key, not by copying the source integer** — Rooms→Departments,
   Materials→Organisms, TestWorkflowSteps→TestDefinitions/MediaTypes/Organisms,
   Media→MediaTypes/Equipment, Specifications→Items, TestWorkflowStepMedias→TestWorkflowSteps
   all resolve their parent via `JOIN ... ON parent."BusinessKey" = v.businesskey`. This means
   the migration is correct even if a parent row's Id in Neon differs from its Id in the
   source DB (e.g. Neon already has "Escherichia coli" seeded under a different Id).
4. **The pre-flight admin check** aborts the whole transaction before any writes if there's no
   `admin` user to attribute audit columns to.
5. **Materials/TestWorkflowStepMedias/Media → Materials** is the one place business-key
   resolution isn't possible (see caveat below) and the script falls back to the literal
   source Id. To stop that literal Id from silently attaching to an unrelated production row,
   Media and TestWorkflowStepMedias additionally verify
   `EXISTS (SELECT 1 FROM "Materials" WHERE "Id"=<id> AND "MaterialName"=<name> AND "BatchNumber"=<batch>)`
   before inserting — if the Id is occupied by something else, the row is skipped rather than
   miswired.
6. **Post-migration verification query** at the end of the script (outside the transaction)
   compares actual row counts per table to the expected source counts, so any silently-skipped
   row is immediately visible for investigation rather than assumed to have succeeded.

### Known data-quality caveats in the source data (informational, not blocking)

- **Materials has no reliable business key, by design.** `MaterialName + BatchNumber` looked
  like a natural key, but source rows Id 8 and Id 16 are both `"Macconkey broth Purple"` /
  `"6267096"` — **confirmed intentional, not a data-entry error.** Both records are kept as-is;
  neither is merged or dropped. Because of this, Materials rows are inserted guarded by `Id`
  only (no business-key duplicate check), and downstream FKs to Materials (from Media and
  TestWorkflowStepMedias) use the literal source Id plus the identity-verification guard
  described in point 5 above, which correctly disambiguates between Id 8 and Id 16 since it
  checks the specific Id, not just the name/batch pair.
- ~~Specifications has non-unique (ItemId, TestCode)~~ **Resolved.** Item Id 3 ("Osteocare
  Tablet") previously had two `TAMC` spec rows (Id 3 and Id 4, limits 100 vs 1000). This has
  been corrected in the source database: Id 3 is now `TYMC`/100, Id 4 is `TAMC`/1000.
  `(ItemId, TestCode)` is now unique across the whole table, so the script's Specifications
  INSERT now also guards on that business key (in addition to `Id`), matching the pattern used
  for every other table with a clean natural key.
- A few Organisms/TestDefinitions rows have placeholder-looking data (`"----"`, `"..."`) —
  carried through as-is; not something to silently drop without your sign-off.
