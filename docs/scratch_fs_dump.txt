1. Purpose
This Functional Specification defines how the MicroLIMS Document Control module shall satisfy the requirements allocated to Release 1a of Phase 1. It describes the intended system behaviour, data structures, business logic, screens, permissions and controls in sufficient detail to permit development, design review and the authoring of Installation and Operational Qualification protocols.
This specification describes what the system does and how it behaves. It does not define the internal code structure, class design or database migration scripts, which are covered by the Design Specification and the development standards of the MicroLIMS project.
Where this specification makes a design decision that is not directly dictated by a requirement, the decision and its rationale are stated explicitly so that the reasoning is available for review and for future change control.
2. Scope
2.1 In scope for Release 1a
The Document Master register, including document identification, classification, ownership and per-document workflow assignments.
Controlled file storage for document revisions, including file integrity control and prevention of overwrite.
The Document Library and Document Details screens.

Module configuration for document types, departments and sections, review cycles, document numbering and controlled-copy behaviour.
The audit trail data model, immutability controls, global audit trail screen and record-specific audit history.
Role-based access control, record cancellation and voiding, system time handling and data integrity controls.

2.3 FS-1a-105 — Scope boundary control
Release 1a shall not expose any interface, event or data path by which a controlled document, its status or a user training state is read by, injected into or able to influence any laboratory execution module of MicroLIMS (sample receiving, testing, media evaluation, environmental monitoring, inventory or review and approval of laboratory results).
This shall be verified by demonstrating that no laboratory execution module references any Document Control entity or service, and that the Document Control module publishes no domain events consumed outside itself. Satisfies DC-URS-161, DC-URS-162 and DC-URS-163.

The Document Control module is delivered inside the existing MicroLIMS application and shares its runtime, database, authentication and infrastructure. It is not a separate deployable system.

Design decision — reuse of shared services. The audit trail, authentication, session management and electronic signature components already qualified within MicroLIMS shall be reused rather than reimplemented within Document Control. Rationale: a second implementation of any of these controls would require independent validation, would create two designs to defend at inspection, and would risk divergent behaviour between modules.
All laboratory logic and all controlled-state transitions are owned by the backend. The frontend shall not compute, infer or enforce any controlled state, permission or lifecycle decision; it renders state returned by the backend and issues intent to the backend.
5. Security and Access Control
5.1 FS-1a-110 — Authentication of controlled actions
Every request that creates, modifies, cancels or voids a Document Control record shall be executed under an authenticated MicroLIMS user identity established by the existing authentication service. Requests without a valid authenticated session shall be rejected by the backend with no partial effect. The authenticated user identity and the server-generated timestamp shall be recorded on the resulting record and its audit event. Satisfies DC-URS-143 and DC-URS-145.
5.2 FS-1a-111 — Permission model
Authorisation is evaluated on the backend for every endpoint. A permission check failure returns an authorisation error and creates no record change. The frontend hides or disables actions the user cannot perform, but this is a usability measure only and is never the enforcement point.

Design decision — RevisionNumber is stored as text, not as an integer. Rationale: company revision conventions include leading zeros ("05") and may include alphanumeric forms. Storing the value as entered preserves the record exactly as issued, and sort order is handled by a separate sequence value rather than by numeric interpretation of the label.
Design decision — CurrentEffectiveRevisionId is stored on the Document Master as an explicit pointer rather than derived at query time from revision statuses and dates. Rationale: a derived value can silently return two effective revisions if any status is inconsistent, whereas a single explicit pointer makes "current effective" unambiguous and directly testable. The pointer is set only by controlled transitions, which are delivered in Release 1b. Satisfies DC-URS-010.
6.2 FS-1a-131 — Per-document workflow assignments
Each Document Master shall record its Document Owner and may record designated Author, Technical Reviewer and Approver assignments. In Release 1a these assignments are captured, displayed, editable by the Document Controller, and audit-trailed. They are not yet enforced, because no review or approval action exists until Release 1b.
The Functional Specification for Release 1b shall define enforcement such that a controlled workflow action requires both the applicable global permission and an active assignment of the corresponding role on that Document Master, and such that the same user cannot hold effective authority for author, technical review and approval of the same revision. Satisfies DC-URS-168 in this release, and provides the structure required by DC-URS-164 to DC-URS-167.
6.3 FS-1a-125 — Record origin
Every DocumentMaster, DocumentRevision and RevisionFile shall carry a RecordOrigin attribute with the values Native or Migrated. Records created through the Register New Document function shall be set to Native and the value shall be immutable thereafter. The Migrated value is written only by the migration function delivered in Release 1e. Record origin shall be displayed on the Document Details screen and shall be available as a Document Library filter. Satisfies DC-URS-193.
6.4 FS-1a-120 — Document identification
Two identifiers are maintained for every Document Master and they are never merged, derived from one another, or substituted for one another:
Company Document Code — the organisation-issued code (for example SOP/QC/MIC/014). Entered manually by the user. Unique across active Document Masters, compared case-insensitively and with surrounding whitespace removed. Never generated or overwritten by the system.
MicroLIMS Document ID — generated by the system, unique, permanent, and unchanged across every revision of the Document Master.
Satisfies DC-URS-003, DC-URS-005 and DC-URS-137.
6.5 FS-1a-121 — MicroLIMS Document ID generation
The identifier is composed from the configured prefix and number format, for example DOC-000217. Generation rules:
The sequence value is allocated from a database sequence within the same transaction that inserts the Document Master, so that concurrent registrations cannot receive the same value.
Uniqueness is additionally enforced by a unique database constraint. A violation aborts the transaction; no partial record is created.
A sequence value consumed by a transaction that subsequently fails is not reissued. Gaps in the sequence are permitted, are not errors, and shall not be backfilled.
The identifier is written once and is immutable. No application function updates it.
Changing the prefix or number format affects only identifiers generated after the change. Existing identifiers are never regenerated.
Satisfies DC-URS-004, DC-URS-005 and DC-URS-136.

8. Controlled File Management
8.1 FS-1a-160 — File storage model
Files are stored in a server-side controlled store that is not addressable by end users. The database holds the file record; the store holds the bytes. Each RevisionFile row is bound to exactly one DocumentRevision, and a file is never shared between revisions. A revision may hold at most one active controlled PDF and at most one active source file. Satisfies DC-URS-021, DC-URS-022 and DC-URS-023.
8.2 FS-1a-161 — File integrity
On upload the system computes a SHA-256 hash of the received file content and stores it on the RevisionFile record together with the byte size. The storage key is derived from the hash, so identical content resolves to the same stored object and no write operation can overwrite different content at an existing key.
On every retrieval the system verifies the stored hash against the content being served. If verification fails, the file shall not be served, an error shall be returned to the user, an audit event shall be raised, and a notification shall be sent to administrators. Upload, hash generation, retrieval and any verification failure are recorded in the audit trail. Satisfies DC-URS-198, DC-URS-199 and DC-URS-200.
8.3 FS-1a-162 — Prevention of overwrite and silent replacement
The file store is append-only. No application function updates or deletes a stored object.
Replacing a file on a Draft revision creates a new RevisionFile row, sets it active, and sets the previous row inactive with a SupersededByFileId pointer. Both rows and both stored objects are retained.
Files belonging to a revision in any state other than Draft cannot be replaced through any application function. The endpoint rejects the request based on revision state evaluated on the backend.
Every file replacement raises an audit event identifying the previous and new file name, size and hash. A file change is therefore never silent.
Satisfies DC-URS-024 and DC-URS-025. Both requirements are rated High risk and require negative testing: an attempted replacement on a non-draft revision, and confirmation that the historical file remains retrievable and unchanged after a draft replacement.
8.4 FS-1a-163 — Access to files and controlled copies
Access to the source (editable) file is permission-controlled per FS-1a-111 and is separate from access to the controlled PDF. Controlled-copy behaviour — whether download is permitted, whether printing is permitted, and whether a watermark is applied on download — is configurable by an administrator (see F-04.5) and is enforced by the backend when the file is served, not by the viewer. Satisfies DC-URS-028 and DC-URS-029.

9.3 FS-1a-182 — Immutability
Audit records are append-only and are protected at the persistence layer rather than by application logic alone:
The application database role is granted INSERT and SELECT on the audit tables only. UPDATE and DELETE are not granted.
A database trigger on the audit tables raises an exception on any UPDATE or DELETE attempt, so the control holds even if privileges are later altered.
No application endpoint exists that updates or deletes an audit record. The audit trail screen is read-only and provides no edit or delete action.
Design decision — enforcement at the persistence layer rather than in application code. Rationale: DC-URS-127, DC-URS-128 and DC-URS-152 are rated High risk with low detectability. A control that lives only in application code can be bypassed by any future code path, and its failure would be silent. A database-level control is testable directly and independently of the application.
Satisfies DC-URS-127, DC-URS-128 and DC-URS-152.

10. Record Cancellation and Voiding
10.1 FS-1a-170 — Prohibition of deletion
No application function shall permanently delete a Document Master, Document Revision, Revision File, configuration record or audit record. No delete endpoint shall exist for these entities. Removal from active use is achieved only through the controlled cancellation and voiding functions defined below. Satisfies DC-URS-184.
10.2 FS-1a-171 — Cancelling a draft revision
A user with the applicable permission may cancel a revision in Draft state. A reason of at least ten characters is mandatory. On cancellation the revision moves to Cancelled, becomes read-only including its files, is excluded from active work lists, and an audit event records the previous status and the reason. Cancelled revisions cannot be reopened; a new draft revision is created instead. Satisfies DC-URS-185.
10.3 FS-1a-172 — Voiding a Document Master
A Document Master registered in error may be voided by the Document Controller. A reason of at least ten characters is mandatory. Voiding is permitted only where the Document Master has never held an effective revision; a Document Master that has been effective is withdrawn through obsolescence in a later release, not voided.
The MicroLIMS Document ID of a voided Document Master is retired permanently and shall not be reissued, because the sequence never reuses a consumed value (FS-1a-121). The Company Document Code of a voided Document Master is released and may be registered again, since the organisation may legitimately reissue it; the uniqueness constraint therefore applies across active Document Masters only. Satisfies DC-URS-186.
10.4 FS-1a-173 — Visibility of cancelled and voided records
Cancelled revisions and voided Document Masters are excluded by default from the Document Library, search results, counts and active work lists. They remain retrievable by authorised users through an explicit "Include cancelled and voided" filter, and are displayed read-only with a clear status indication and the recorded reason. Satisfies DC-URS-187.
10.5 FS-1a-174 — Audit of cancellation and voiding
Cancellation and voiding record the performing user, the server-generated date and time, the previous status and the mandatory reason, and raise an audit event. The reason text is stored on both the record and the audit event. Satisfies DC-URS-188.
11. Data Integrity and Time Handling
11.1 FS-1a-190 — Enduring records and traceability
Document Masters, revisions, files and audit events are enduring records. No application function reduces, summarises or removes them. Every revision is permanently linked to its Document Master, every file to its revision, and every audit event to the affected record, so that any controlled record can be traced to the exact revision it relates to. Records are retrievable and legible through the application for the full retention period without dependence on the originating user session. Satisfies DC-URS-149, DC-URS-153 and DC-URS-154.
11.2 FS-1a-195 — Date and time
All timestamps on controlled records and audit events are generated by the database server, not by the client and not by the application server. Values are stored in UTC with time zone information.
A single system time zone is held in module configuration and is used for all display and for the evaluation of all date-driven controlled transitions in later releases. It is changeable only by a System Administrator and the change is audit-trailed. Client-supplied timestamps are never accepted for controlled records. Satisfies DC-URS-151 and DC-URS-182.
Design decision — server-generated timestamps only. Rationale: a client-supplied timestamp is under the control of the user performing the action, which defeats contemporaneity and attributability, and the failure is invisible in the resulting record.

12.5 F-05 — Audit Trail
F-05.1 — Global audit trail
A searchable, read-only view of all Document Control audit events. Filters: date range, user, action category, record type, document type, department and section, company document code, MicroLIMS Document ID, revision, and event identifier. Free-text search across searchable event attributes. Results are paged server-side and display date and time, user, action, record type, document, revision, previous value, new value, source context and event identifier. Selecting an event displays its full detail including all changed fields.
Export produces a file of the currently filtered result set and is itself audited, recording the filter criteria applied and the number of records exported. The screen presents no edit or delete action and the backend exposes no endpoint capable of modifying an audit record. Satisfies DC-URS-129 and DC-URS-127.
F-05.2 — Record audit history
Accessible from the Document Details screen, showing all audit events for that Document Master and all of its revisions, in reverse chronological order, using the same event detail presentation. Satisfies DC-URS-130.
13. Non-Functional Design
13.1 FS-1a-200 — Infrastructure, availability and retention
The module uses the established MicroLIMS application hosting, database, authentication, backup, restore and retention infrastructure. It introduces no separate database, no separate authentication mechanism and no separate backup arrangement. The controlled file store is included in the MicroLIMS backup scope, and restore testing shall demonstrate that database records and their corresponding stored files are recovered consistently. Satisfies DC-URS-155 and DC-URS-160.
13.2 FS-1a-201 — Performance
Document Library search and record opening shall complete within an agreed response time under the expected concurrent load. Filtering, sorting and paging are performed server-side so that response time does not degrade as the register grows. The specific response time target and load profile shall be stated in the PQ protocol. Satisfies DC-URS-159.
13.3 Error handling
All validation and authorisation failures are evaluated on the backend and returned as structured errors that the frontend presents in context. A rejected request creates no record and no partial state. Any operation that writes to both the database and the file store is executed such that a failure in either leaves no orphaned record and no unreferenced stored object.

15. Assumptions, Constraints and Open Items
15.1 Assumptions
The MicroLIMS authentication, session management, audit trail infrastructure and role framework are already implemented and validated, and are available for reuse.
Users, departments and roles are maintained through existing MicroLIMS administration and are not duplicated within Document Control.
The controlled file store is included in the existing MicroLIMS backup and restore scope.
15.2 Constraints
Documents registered in Release 1a remain in Draft until the approval workflow is delivered in Release 1b. This is a deliberate design decision recorded in FS-1a-140 and is accepted by the project.
Release 1a delivers no laboratory execution integration of any kind (FS-1a-105).
