# A3 — User Manual, SOP Templates and Screenshots: Design Specification

**Roadmap package:** A3 (`improvement-roadmap.md`)
**Status:** Approved by the user 2026-11-11
**Date:** 2026-11-11
**Related:** A1 (requirement IDs), C6 (in-app help reads the manual).

## 1. Purpose

Give each role a short task-based guide, put the whole manual in `documents/UserManual`, give the site SOP templates for running the system, and produce every screenshot by a script so they can be refreshed after any interface change.

## 2. Decisions (confirmed by the user, 2026-11-11)

| # | Decision | Answer |
|---|---|---|
| 1 | Manual | Keep the 44 module chapters as the reference; add one task-based guide per role; move everything into `documents/UserManual` |
| 2 | SOP templates | System use; account management; backup and restore; periodic review; incident handling; electronic signatures; audit trail review; change control and release; business continuity |
| 3 | Screenshots | A Playwright script against a local system with made-up demo data |
| 4 | Language | English only (Arabic comes with package F4) |

## 3. Out of scope

- Rewriting the 44 chapters. Errors found while writing the role guides are corrected; gaps are listed.
- Approved SOPs. A3 delivers templates with marked blanks; the site completes, numbers and approves them.
- Laboratory method SOPs (how to perform a test).
- End-to-end automated tests. The screenshot script is not a test suite.
- Arabic, video, training records.

## 4. Current state (from the repository, not run)

- `documentation/guide/`: 44 chapters (about 10,500 lines), each with fixed sub-headings, written with made-up names only. Images point to `../screenshots/`.
- `documentation/SCREENSHOT_PLAN.md` lists 123 screenshots; 74 exist in `documentation/screenshots/`; the rest are placeholders. No script that takes them is in the repository, and Playwright is not a project dependency.
- `documentation/DOCUMENTATION_GAPS.md` lists 55 gaps, 9 of them differences between a specification and the code.
- `documents/UserManual`, `documents/SOP` and `documents/Screenshots` hold only a README.
- Seeded data: roles, permissions, one administrator, master data and one example item. **No samples or results.** There is no docker-compose file.
- System roles: System Administrator, Section Head, Reviewer, Analyst, QC Manager. There is no separate QA role (the roadmap says "QA"; the guide is written for QC Manager).
- Features the SOPs refer to exist: access review with export, password policy setting, account lock after failed attempts, idle sign-out, backup and restore scripts with a backup-run record, audit trail search and export, error monitoring with incidents, logged system-setting changes.
- No laboratory deviation or CAPA module exists (roadmap package D2).

## 5. Design

### 5.1 Layout

```
documents/UserManual/
  README.md                 how the manual is organised; status; version
  roles/analyst.md, reviewer.md, section-head.md, qc-manager.md, system-administrator.md
  reference/01-introduction.md … 44-glossary.md      (moved from documentation/guide)
  USER_MANUAL.md            combined file, generated
documents/Screenshots/      all pictures, generated by the script
documents/SOP/templates/    nine SOP templates
tools/screenshots/          the script and its demo-data setup
```

`documentation/guide` and `documentation/screenshots` keep a pointer file. Package C6 reads the manual from the new place; its plan is updated in this package.

### 5.2 Role guides

- One file per role, 300 to 500 lines, organised by **task**, not by screen.
- Each task: when you do it, before you start, numbered steps (one action each), what the system checks or refuses and why, what happens next, and a link to the reference chapter for detail.
- Tasks per role:

| Role | Tasks |
|---|---|
| Analyst | Sign in and find my work; receive a sample; start and record a count test; record a pathogen step; read an incubation; enter a physicochemical result; record EM and water readings; prepare media or a solution; correct an entry; sign |
| Reviewer | Find what waits for me; review a sample; return to the analyst; why I cannot review my own work; read the audit trail of a record |
| Section Head | Assign work; approve or reject; set up an item, specification and test; manage equipment and media release; monitoring plan; handle an out-of-limit result; reports and certificates |
| QC Manager | Dashboards and KPIs; approvals reserved for the role; trends; audit trail review; periodic review inputs |
| System Administrator | Create and disable users; roles and sections; password and lock settings; access review; system settings; backups; error monitoring; what the administrator cannot do (laboratory decisions) |

- Tasks are written from the reference chapter **and checked against the code** (permission, refusal message, status change). A step that could not be confirmed is marked for the reviewer, in the style the guide already uses.
- Wording rules of the existing guide stay: plain English, made-up names only, no claim that the system is "validated" or "compliant".
- Each task lists the A1 requirement IDs it relates to in a hidden comment, so A2 can show manual coverage.

### 5.3 Reference chapters

Moved unchanged with history. Picture links are updated to the new folder. Chapters keep their numbers, so in-app help mappings stay valid.

### 5.4 Screenshot script

- A separate small Node project in `tools/screenshots/` using Playwright, so the product's own dependencies do not change.
- **Demo data is created through the application's own API**, signed in as real demo users with the proper roles, against a throwaway local database: users per role, an item with specifications, tests, media, equipment, then samples moved through receipt, testing, review and approval by different users. Nothing is inserted directly into the database, so every record is one the system itself accepted. No production code is added for this.
- Demo names follow the guide's convention (Product A, Lot L-0001, Analyst A). The script refuses to run unless the API address is `localhost`, so it cannot run against a real system.
- One entry per screenshot in a list file: ID (the existing `SS-NNN`), file name, role, route, the actions to reach the state, what must be visible before the picture is taken, optional highlight.
- Fixed window size, light theme, animations off, fixed browser time zone, and the clock shown in data masked where it would change every run, so pictures change only when the interface changes.
- The script takes all 123 planned pictures where the feature exists. A picture that cannot be taken is reported by ID with the reason; the run does not silently skip it.
- A check compares the list file, the picture folder and the links in the manual: a link to a missing picture, or a picture nobody uses, is reported.
- Run by hand before a release (`npm run capture`), not on every commit. A manual CI job is provided.

### 5.5 SOP templates

Nine templates in one layout: header (number, title, version, effective date, author, reviewer, approver — all blank), purpose, scope, responsibilities by role, definitions, procedure, records, references, change history.

| Template | What the procedure section covers |
|---|---|
| System use | Sign-in, own account only, data entry at the time of work, corrections with reason, sign-out, what to do when the system refuses an action |
| Account management | Request and approval, creation, role and section assignment, change, disabling leavers, password reset, lock and unlock, periodic access review using the built-in review |
| Electronic signatures | Meaning of each signature, user accountability statement, password secrecy, what a signature shows on screen and print |
| Audit trail review | What is reviewed, by whom, how often, how to search and export, what to do with a finding |
| Backup and restore | Schedule, running and checking a backup, restore test, records |
| Periodic review | Frequency, inputs (incidents, changes, access reviews, audit findings, open deviations), output and decision |
| Incident handling | Reporting, the system's error-monitoring records, classification, escalation, closure |
| Change control and release | Request, impact and risk assessment, testing and matrix, approval, installation with IQ, release note |
| Business continuity | Working on approved paper forms when the system is down, later entry by the original analyst with reason and second-person check, reconciliation |

- Each step says **which screen or function** performs it, taken from the code.
- **Values the site must decide are marked blanks** `[SITE TO DEFINE: …]`: frequencies, retention times, responsible job titles, form numbers. Where the system has a current setting (for example password length, lock duration, idle time) the template names the setting and shows today's default, marked "current default — confirm".
- Each template starts with: "Template. Not an approved procedure until completed and approved by the site."

### 5.6 Combined manual and checks

A script builds `USER_MANUAL.md` from the role guides and chapters. A check, added to the A1 document check, fails when: a link between manual files is broken; a picture link has no file; a role-guide task has no reference link; a template still lacks a required heading. CI runs it.

## 6. Risks

| Risk | Handling |
|---|---|
| A role guide describes a step wrongly | Each task checked against code; unconfirmed steps marked; QA and a user of that role review |
| Template taken as an approved SOP | Fixed first line; blanks cannot be missed; status in the index |
| Demo setup breaks when the interface or API changes | The setup uses the API with typed calls and fails loudly at the failing step; it is run before each release |
| Pictures show real data | Script runs only against localhost with data it created itself |
| Moving the guide breaks C6 | C6 plan updated here; chapter numbers unchanged |

## 7. Done when

Five role guides exist and pass the checks; the 44 chapters and all pictures are under `documents/`; one command recreates the pictures from an empty database; nine SOP templates exist; the list of pictures that could not be taken and of manual gaps has been given to the user.
