### MOD-WORKBOOK-001 Master Data Workbook
- Purpose: Bulk data onboarding and migration tool using an Excel workbook (`.xlsx`); allows downloading current master data with instruction and choices sheets, dry-run checking (validation report table with sheet summaries and row-level errors), signed loading with electronic signature (`SignatureMeaning.MasterDataChanged`), and second-person verification (`SignatureMeaning.Reviewed`) that activates newly loaded items and materials; strictly add-only, transactions with savepoints per row, max 10 MB file size, max 5,000 new rows. Any row error in a signed load rolls the whole load back (nothing is half-loaded; see BR-WORKBOOK-004). Status: IMPLEMENTED. Lab scope: cross-laboratory (Microbiology, Physicochemical FP and RM&PM). [src: frontend/src/modules/laboratoryConfiguration/masterDataWorkbook/MasterDataWorkbookPage.tsx:L12-L114; backend/MicroLIMS.Application/Services/MasterDataWorkbook/MasterDataWorkbookService.cs:L16-L284; backend/MicroLIMS.Application/Services/MasterDataWorkbook/MasterDataWorkbookRunner.cs:L6-L122]

### WF-ITEM-001 Configure an item and its tests
- Start / trigger: a Section Head (or System Administrator) needs a new product, raw material or packaging material that the laboratories will receive and test, or needs to change which tests it carries.
- Who: a user holding `Items.Manage` (route and every item action on the server). Document upload needs `Items.DocumentUpload` in addition.
- Prerequisites: the tests to assign already exist in the Test Master (physicochemical tests: WF-TESTMASTER-001; microbiology tests: cluster C4). For a new item the item code must not exist. Samples are not involved.
- Required data: Item Name, Item Code, Category (defaults to Product), at least one Assigned Test (dialog rule only, see GAP-710). Optional: SOP Number, documents, preparation configuration (WF-ITEM-003), specifications (WF-ITEM-002).
- Steps:
  1. Open the sidebar entry "Items" (group GENERAL LABORATORY CONFIGURATION). System: loads all items (any authenticated user may read the list) and shows the register with search "Search by item name, item code, SOP number...", a Category filter, a Status filter, and the empty states "No items configured yet" / "No items match your filters" [src: frontend/src/routes/menuConfig.ts:L210; frontend/src/modules/laboratoryConfiguration/items/ItemTable.tsx:L81-L94].
  2. Click "Add Item". System: opens the dialog "Add New Item".
  3. Fill "Item Name", "Item Code", optionally "SOP Number", choose "Category" (Product, Raw Material, Packaging Material) and choose one or more tests in "Assigned Tests". The picker lists active Test Master entries as `{code}: {display name}`; typing an unknown code offers `+ Add "{text}" to Test Master`, which creates a Test Master entry from the item dialog (see GAP-714 and the warning below).
  4. Click "Save Item". Validation (client): `Item Name, Item Code, and at least one assigned test are required.` Validation (server): category must be one of the three (`Items can only be configured for Product, Raw Material, or Packaging Material categories. ...`); code unique (`An item with code '{code}' already exists.`). Test codes are NOT checked against the Test Master by the item save (they are checked later, at sample receipt).
  5. System: creates the item with status Active, stores each assigned test with its code as the display name, writes the generic audit row, shows `Item "{name}" created successfully.` and selects the new item, opening its workspace (tabs Overview, Assigned Tests, Specifications, Documents & Attachments, Preparation Configuration, Audit History) [src: frontend/src/modules/laboratoryConfiguration/items/ItemsPage.tsx:L120-L145; backend/MicroLIMS.Application/Services/ItemService.cs:L35-L54].
  6. Next action (optional): upload controlled documents. In the tab "Documents & Attachments" click "+ Upload SOP" or "+ Upload Verification Report"; in the dialog choose "Document Type", "Version" (default "Rev 01", required), "Effective Date" (defaults to today) and a file (pdf, Word, Excel or image, up to 25 MB), click "Upload". Without a file: `Please select a document file to upload.` System: stores the file and its SHA-256, marks the new document Current and the previous Current document of that type Superseded; View and Download actions are logged per user. Permission: `Items.DocumentUpload`. No signature.
  7. Next action (optional): configure the preparation protocol (WF-ITEM-003) and the specifications (WF-ITEM-002).
  8. Editing: row action "Edit item" opens "Edit Item: {name}" with the same fields; "Save Changes" replaces the whole assigned-test list (a stale form is refused with `This record was changed by someone else while you were working on it. Nothing was saved - reload it and make your change again.`); success text `Item "{name}" updated successfully.` [src: backend/MicroLIMS.Application/Services/ItemService.cs:L62-L82; backend/MicroLIMS.API/Middleware/ExceptionMiddleware.cs:L17-L18].
  9. Retiring: "Freeze item" sets the item Frozen at once (no confirmation, `Item "{name}" frozen.`); the next receipt attempt is refused (`Item '{name}' is frozen and cannot be used to receive new samples.`). "Unfreeze item" restores it. "Delete item" asks `Delete item "{name}" ({code})? This cannot be undone. If it has already been used to receive samples, deletion will be blocked - freeze it instead.` and is refused by the server once any sample used the item.
- Review / Approval: none. There is no second-person review, reason or signature for item changes (verified; SOP section 10 says otherwise: DISCREPANCY, see GAP-705).
- Final state: item Active with its tests; the next sample received for it creates one test order per assigned test (WF for sample receiving is in another cluster).
- Blocking conditions: duplicate code; wrong category; zero tests at receipt (`Item '{name}' has no assigned tests. ...`); frozen item; a test code missing from the Test Master at receipt.
- Permissions per step: list read = any signed-in user; add / edit / freeze / unfreeze / delete = `Items.Manage`; upload = `Items.DocumentUpload`; view / download = any signed-in user.
- Signature points: none. Audit: generic audit rows for the item, its tests and documents; document views and downloads are logged.

### WF-ITEM-002 Maintain item specifications
- Start / trigger: a Section Head needs to set, change or remove the acceptance limits of a test on an item (for example after a revised specification document).
- Who: the route needs `Items.Manage`; saving needs `MasterData.Manage` and, for non-administrators, membership of the section that owns the test (the Test Master section of the test code). Rows of the other laboratory are shown read-only.
- Prerequisites: the item exists; the test is assigned to the item (WF-ITEM-001); for HPLC, ICP, dissolution, disintegration, weight variation and titration tests the Test Master row (and method) already exists (WF-TESTMASTER-001 and the method screens); a Finished Product item for stage-specific rows.
- Required data per limit type: see the dialog field list in the screens section; always "Assigned Test", "Parameter Name", "Limit Type". Optional: Reference Standard, Unit, Production Stage (Finished Product items only), Dilution Factor (Count-Tiered only).
- Steps:
  1. Open the item (WF-ITEM-001 step 1), select it, open the tab `Specifications ({N})`. System: lists rows grouped per assigned test with chips; tests with no row show nothing; empty text `No specifications defined yet. Click "Add Specification Parameter" above to add limits.`
  2. Click "Add Specification Parameter" (or `+ Add parameter to {test}`). System: dialog "Add Specification Parameter". Choose "Assigned Test *"; the Limit Type preset follows the test's workflow type (Count test -> Count-Tiered; Observation -> Presence / Absence; Dissolution -> Dissolution Q; Disintegration -> Disintegration Time; Weight Variation -> Weight Variation; otherwise Range).
  3. Enter "Parameter Name *" and the fields of the chosen limit type (Range: "Lower Limit (NLT) *", "Upper Limit (NMT) *" and the two inclusive checkboxes; NMT; NLT; Target +/- Tolerance; Count-Tiered "Alert Limit" / "Action Limit" / "Specification Limit *"; Qualitative text; Presence / Absence; Multi-Stage criteria; Dissolution Q; Disintegration Time; Weight Variation). For HPLC method assay tests also "Analyte *" and "Basis *" (and label claim when the basis is amount per unit); for GC residual solvents the limit type is fixed to a not-more-than limit in ppm; ICP and titration add their basis fields.
  4. Click "Add Parameter" (or "Save Changes" when editing). Validation: the dialog checks required fields and the specialised rules (messages in the validations section); the server repeats and extends them: ownership of the test's section (`This specification belongs to {labName} - only its Section Head can change it.`), test assigned to the item (`Test '{code}' is not assigned to item {id}.`), area fits the item category, duplicate parameter, stage rules, limit-type rules.
  5. System: for every limit type except Count-Tiered, writes the canonical limit text into the specification limit and empties alert, action and dilution; saves the row and the generic audit row; refreshes the list. No signature, no reason. Status change: none (a specification has no status).
  6. Edit: icon button "Edit Specification" (tooltip) opens "Edit Specification Parameter"; the assigned test is locked; a stale form is refused with the concurrency message above. Delete: icon button "Delete Specification" asks `Delete specification parameter "{parameter}" for "{item}"? This cannot be undone.` and removes the row; the failure fallback is `Failed to delete specification.` [src: frontend/src/modules/laboratoryConfiguration/items/components/ItemSpecificationsSection.tsx:L315-L336, L978-L987; backend/MicroLIMS.Application/Services/MasterData/SpecificationMasterDataService.cs:L72-L208].
- Review / Approval: none in the application. Results already recorded keep the limits copied at calculation time; new results use the saved rows (stage-specific rows replace the every-stage rows for a sample whose stage role has rows).
- Final state: the item has the acceptance limits that result entry compares against: Range / NMT / NLT / Target use inclusive limits unless the checkbox is cleared (a value equal to an inclusive limit passes); Count-Tiered values equal to a limit pass; Specification limit exceeded is out of specification, then action, then alert.
- Blocking conditions: section ownership; test not assigned; duplicate parameter; stage rows only for Finished Product items; one specification per dissolution / disintegration / weight variation test and stage role; analyte or element not belonging to the test's method.
- Permissions per step: reading = any signed-in user; add / edit / delete = `MasterData.Manage` + section membership (or System Administrator).
- Signature points: none (DISCREPANCY against SOP section 10, GAP-705).
- INTENDED source: docs/Universal_Specifications_Build_Spec.md (limit types, canonical text, evaluation, duplicate refusal, assigned-test rule, Item workspace tab) [src: docs/Universal_Specifications_Build_Spec.md:L53-L90]; the later limit types (dissolution, disintegration, weight variation, method assay bases, stage roles) have no specification found: REQUIRES CONFIRMATION.
- Steps that REQUIRE CONFIRMATION: labels of the ICP, residual-solvent and titration basis fields; the exact confirmation dialog buttons; the physchem per-user area is not enforced (GAP-708).

  3. Click "Verify". System: opens the signature dialog with the statement `I verified this load against the approved source documents.`; if the load created items that have no specification yet it adds `Note: these items have no specifications yet and will become usable: {item codes}.`

Stage replicates need the production stages of WF-RECVCFG-001.
- Required data: Code, Display Name, Section, Workflow Type (default HPLC method assay), Equation Type (filtered to fit), the type-specific box, and the area checkbox (default: the page's own area).
- Steps:
  1. Open the sidebar group "Physicochemical Configuration" and its entry "FP Test Master" or "RM & PM Test Master" (routes `/laboratory-configuration/fp-test-master`, `/laboratory-configuration/rm-pm-test-master`). System: lists tests of the Finished Product section whose area includes the page's area.
  2. Click "Add Test". System: dialog "Add Test"; the section is preselected when the user has only one.
  3. Enter "Code" and "Display Name", choose "Section", "Workflow Type" and "Equation Type" (changing one presets the other and the suitability switch), fill the type box: HPLC method (and read-only abbreviation) / ICP method / replicate count and evaluation basis / tare and condition fields / dissolution offsets and abbreviation / disintegration units / weight variation bands / titration settings. Tick "Also used for RM & PM" (or "Also used for FP") if the test serves both areas.
  4. Click "Add Test". Validation (client): `Both Code and Display Name are required.`, `Laboratory section is required.`, then the type-specific messages; (server) duplicate code, workflow/equation coupling, suitability rules, method existence / same section / active, replicate and stage rules, area required, section membership - all listed in the validations section.
  5. System: creates the test (Active), writes the generic audit row, shows `Test "{code}" added to the Test Master.` and closes the dialog. Status change: none other than Active.
  6. Next action: reopen the row with "Edit" to configure "Replicates per stage" (the box says `Save this test first to configure replicates per stage.` while adding). Titration tests do not show this box.

Editing an existing test: "Edit" -> change -> "Save Changes" -> `Test "{code}" updated.` If the test is or becomes a Titration test and any titration setting (or the area) changed, the field "Reason for Change" (5-500 characters) appears and is required; the server records the audit event `TestDefinition.TitrationChanged` with before and after values and the reason.   8. Freeze: row action "Freeze" (no confirmation) -> `Test "{code}" frozen.`; the test disappears from pickers for new selections; existing records are unaffected; "Unfreeze" reverses it.

- BR-SPEC-002 Canonical Limit Formatting. IMPLEMENTED (verified). Numbers are written with the invariant culture (dot decimal), without trailing-zero trimming:
  - `Range`: `{LowerLimit}-{UpperLimit}`; `NotMoreThan`: `NMT {UpperLimit}`; `NotLessThan`: `NLT {LowerLimit}`; `TargetWithTolerance`: `{Target} ± {Tolerance}%` (Percent mode) or `{Target} ± {Tolerance}` (Absolute); `Qualitative`: the expected result text; `PresenceAbsence`: `Present` or `Absent`; `MultiStage`: empty (criteria are in the stage rows); `DissolutionQ`: `Q = {LowerLimit} %`; `DisintegrationTime`: `NMT {UpperLimit} min`; `WeightVariation`: `USP <2091>: tablets, limit by average weight` (Tablet) or `USP <2091>: net content 90-110 % of average` (Capsule). `CountTiered` keeps the typed `SpecLimit`, `AlertLimit`, `ActionLimit` and `DilutionFactor` [src: backend/MicroLIMS.Application/Services/SpecificationService.cs:L36-L72].
  - INTENDED (Build Spec "Canonical SpecLimit text") matches for the eight original types [src: docs/Universal_Specifications_Build_Spec.md:L53-L62].
- BR-SPEC-003 Limit Comparison and Evaluation Logic. IMPLEMENTED (verified). `SpecificationEvaluator.Evaluate(spec, value)` takes a `decimal` and performs no rounding of its own; comparisons are exact decimal comparisons. Results are `ResultStatus` values:
  - `Range`: if neither limit is set -> `LimitsNotConfigured`. Lower: with `LowerInclusive` the value is out when `value < LowerLimit` (equal is within); without it, out when `value <= LowerLimit`. Upper: with `UpperInclusive` out when `value > UpperLimit`; without it out when `value >= UpperLimit`. Otherwise `WithinLimits`. A missing single bound is skipped.
  - `NotMoreThan`: no upper limit -> `LimitsNotConfigured`; out when `value > UpperLimit` (inclusive, the default) or `value >= UpperLimit` (exclusive). `NotLessThan`: no lower limit -> `LimitsNotConfigured`; out when `value < LowerLimit` (inclusive) or `value <= LowerLimit` (exclusive).
  - `TargetWithTolerance`: target or tolerance missing -> `LimitsNotConfigured`; tolerance `tol = Target * Tolerance / 100` in Percent mode, else `Tolerance`; out when `value < Target - tol` or `value > Target + tol` (the band edges are inclusive passes).
  - `CountTiered`: `SpecLimitParser.Compare` parses the three text limits (supported shapes: a plain number, which means an upper bound; a range `a-b`; `NMT x`; `NLT x`; `a ± b` or `a +/- b`, with an optional `%` after the tolerance; an unparseable text means "no limit" and never throws). The order is Specification first (exceeded -> `OutOfSpecification`), then Action (`ActionLimitExceeded`), then Alert (`AlertLimitExceeded`); if none of the three has a limit -> `LimitsNotConfigured`; otherwise `WithinLimits`. "Exceeded" is strict (`value < Min` or `value > Max`), so a value equal to a configured boundary passes [src: backend/MicroLIMS.Application/Services/SpecLimitParser.cs:L18-L22, L206-L228].
  - `Qualitative`, `PresenceAbsence`, `MultiStage`, `DissolutionQ`, `DisintegrationTime`, `WeightVariation` throw `InvalidOperationException` ("is not numeric and cannot be evaluated against a numeric value"); those tests have their own evaluators.
  - Rounding: the two callers read here (`MeasurementCalculator` and `GravimetricCalculator`) pass the unrounded mean/min/max; callers in the HPLC, ICP and other calculators were not all read, so whether any caller rounds before comparing is REQUIRES CONFIRMATION (GAP-712) [src: backend/MicroLIMS.Application/Services/SpecificationEvaluator.cs:L8-L87; backend/MicroLIMS.Application/Helpers/MeasurementCalculator.cs:L92-L117; backend/MicroLIMS.Application/Helpers/GravimetricCalculator.cs:L90-L95].
  - INTENDED (Build Spec "Evaluation"): "WithinLimits / OutOfSpecification for Range (inclusive flags respected), NMT, NLT, Target±Tol; CountTiered -> existing SpecLimitParser.CompareAgainstLimits(...); Qualitative / PresenceAbsence / MultiStage -> throw InvalidOperationException". Code matches; the later limit types are extensions [src: docs/Universal_Specifications_Build_Spec.md:L64-L69]. ## terminology

### MOD-ITEM-001 Items
- Item: A manufactured product or raw/packaging material catalog entry tested by the laboratory. [src: backend/MicroLIMS.Application/Services/ItemService.cs:L18-L23].
- Assigned Tests: The battery of laboratory test definitions linked to an item that are automatically instantiated as sample test orders when a sample for that item is received. [src: frontend/src/modules/laboratoryConfiguration/items/components/AddItemDialog.tsx:L148-L151].
- Frozen Item: A deactivated catalog item whose sample receipt is blocked while preserving all past historical testing data and traceability. [src: backend/MicroLIMS.Application/Services/ItemService.cs:L101-L104].
- Controlled Document: An authoritative standard operating procedure (SOP) or verification report file uploaded to an item, governed by revision versioning and access logging. [src: backend/MicroLIMS.Application/Services/ItemDocumentService.cs:L17-L25].
- Preparation Protocol: Standardized sample preparation configuration (sample amount, technique, filtration/washing volume, diluent, neutralizer) used by analysts during microbiology testing. [src: backend/MicroLIMS.Application/Services/ItemPreparationConfigurationService.cs:L26-L29].

### MOD-SPEC-001 Specifications
- Canonical Limit: Standardized text representation of an acceptance limit (e.g. "90.0-110.0", "NMT 10", "Q = 75 %") automatically formatted and saved by the system. [src: backend/MicroLIMS.Application/Services/SpecificationService.cs:L36-L59].
- Count-Tiered Specification: Multi-threshold limit configuration allowing Alert, Action, and Specification limits with an optional dilution factor, used for microbial enumeration tests. [src: backend/MicroLIMS.Application/Services/SpecificationService.cs:L51, L84-L85].
- Stage-Specific Specification: Acceptance criteria applicable exclusively to samples received at a designated production stage role (Bulk, In-Process, Finished, Stability). [src: backend/MicroLIMS.Application/Services/SpecificationLookup.cs:L8-L14].
- Dilution Factor: A multiplier applied during count evaluation, permitted exclusively on Count-Tiered specifications. [src: backend/MicroLIMS.Application/Services/SpecificationService.cs:L84-L85].

### MOD-RECVCFG-001 Receiving Configuration
- Sampler: An individual qualified to draw samples; configured in a suggestion picklist on the sample receiving form. [src: frontend/src/modules/laboratoryConfiguration/masterDataSimple/ReceivingConfigurationPage.tsx:L308-L310].
- Cause of Testing: Mandatory justification selected upon receiving a sample (the only example in the screen is "Investigation"; the list contents are site data). [src: frontend/src/modules/laboratoryConfiguration/masterDataSimple/ReceivingConfigurationPage.tsx:L321-L323].
- Production Stage Role: Standardized functional classification of a manufacturing stage (`Bulk`, `InProcess`, `Finished`, `Stability`, `Other`). [src: frontend/src/modules/laboratoryConfiguration/masterDataSimple/ProductionStagesCard.tsx:L31-L37].

### MOD-WORKBOOK-001 Master Data Workbook
- Master Data Workbook: An Excel spreadsheet (`.xlsx`) structured into 12 predefined sheets used to bulk-load laboratory master data. [src: backend/MicroLIMS.Application/Services/MasterDataWorkbook/MasterDataSheets.cs:L8-L33].
- Second-Person Verification: A dual-control compliance safeguard requiring an independent qualified user to review and sign off on imported data before it becomes active. [src: backend/MicroLIMS.Application/Services/MasterDataWorkbook/MasterDataWorkbookService.cs:L187-L190].
- Dry Run (Check File): Pre-load validation that executes all row insertions against a transactional savepoint and rolls back, generating a comprehensive error report without modifying database state. [src: backend/MicroLIMS.Application/Services/MasterDataWorkbook/MasterDataWorkbookService.cs:L99-L114].

### MOD-TESTMASTER-001 Test Master (FP and RM & PM)
- Test Definition: Canonical master record defining a test code, display name, owning section, workflow type, equation type, and operating parameters. [src: backend/MicroLIMS.Application/Services/MasterData/TestDefinitionMasterDataService.cs:L30-L34].
- Physicochemical Area: Operational sub-division of the physicochemical laboratory separating Finished Product testing (`fp`) from Raw and Packaging Material testing (`rmpm`). [src: frontend/src/modules/laboratoryConfiguration/masterDataSimple/testMasterArea.ts:L1-L30].
- System Suitability (SST): Instrumental checks (e.g. RSD, resolution, tailing factor, plate count) required before running chromatographic tests. [src: backend/MicroLIMS.Application/Services/MasterData/TestDefinitionMasterDataService.cs:L59-L71].
- Stage Replicate: Minimum number of sample test determinations mandated for a sample based on its reconciled manufacturing stage role. [src: backend/MicroLIMS.Application/Services/MasterData/TestStageReplicateMasterDataService.cs:L48-L53].

## audit-trail

### MOD-ITEM-001 Items
- Automatic Audit Capture (verified, mechanism corrected): `MicroLimsDbContext.SaveChanges` captures every added, modified and deleted entity (except an exclusion list such as audit rows, incidents, error logs, refresh tokens, notification logs and the Material/Equipment document access logs) and writes an `AuditLog` row in the same transaction, with action Create/Update/Delete, the previous values (updates and deletes) and the new values. It is a DbContext override, not an EF interceptor. So item create/update/freeze/unfreeze/delete, item documents (including the `ItemDocumentAccessLog` rows, which are NOT on the exclusion list), preparation configurations, specifications, test definitions, stage replicates, reference lists and workbook import rows are all audited without the service doing anything. - Preparation Configuration approval (verified): records `CreatedByUserId`, `CreatedAt`, `ApprovedByUserId` and `ApprovedAt` on `ItemPreparationConfiguration`; it is NOT an electronic signature (no password, no signature record).
