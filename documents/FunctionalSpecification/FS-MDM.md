## Scope and reading notes

- This document covers the master-data write methods of the items, specifications, Test Master, test workflow steps, stage replicates, master-data workbook, reference lists, organisms, water, environmental monitoring (EM), after-cleaning and media-configuration services. Each entry names the public write methods and the checks they make. It does not list every field.
- Every statement was written from the code files named in each entry. Nothing was run. Pharmacopoeia chapters are pointers only (to be confirmed by QA).
- The code was read as it stands in the working tree on 2026-11-12. That includes the uncommitted change that adds a laboratory-scope check and a version check to Test Master freeze and unfreeze and to the workflow-step methods (`TestConfigurationScope.cs`, `TestDefinitionMasterDataService`, `TestWorkflowStepMasterDataService`). Entries FS-MDM-010 to FS-MDM-014 describe that state.
- Limits, incubation hours, temperatures, dilution factors and equation settings are not fixed in the code. They are configured by the Section Head. Where a number is written in an entry, it is literally in the code.
- Permissions. Every write endpoint of the master-data controllers carries the policy `MasterData.Manage` (`PermissionConstants.MasterDataManage`). The item endpoints carry `Items.Manage`. The controllers are otherwise `[Authorize]` only, so every signed-in user can read.
- Laboratory scope. `IUserSectionScopeService.GetConfigurableSectionIdsAsync` returns null (all sections) for a role that holds `Sections.ConfigureAll`, and otherwise the sections the user is a member of. A null result means no restriction.
- Version check. `RecordVersion.EnsureCurrent` refuses only when the request carried a record version (`If-Match`) and that version differs from the row. It is the stale-form check. Separately, entities with a version column carry an automatic `xmin` concurrency token, so overlapping saves of one row are refused. Where a method lacks `EnsureCurrent`, this document says "no stale-form version check".
- Audit. `MicroLimsDbContext.SaveChangesAsync` writes an audit row for every tracked insert, update and delete of a type that is not in `AuditCaptureExcludedTypes`. None of the master-data entities in this document is in that list, so each save below is audited automatically (user, time, old and new values). The methods that capture a reason or write an extra audit event say so. None of the methods in this document asks for an electronic signature, except the workbook load and verification (FS-MDM-017, FS-MDM-018).

## Functions

### FS-MDM-001
**Satisfies:** URS-MDM-001, URS-MDM-002, URS-MDM-003
**Function:** Permission and scope model of the master-data controllers. Read endpoints (`GET`) need only a signed-in user. Every create, update, delete, freeze, move and workbook endpoint has `[Authorize(Policy = PermissionConstants.MasterDataManage)]`; the item write endpoints have `Items.Manage`; the media-product code change has the role `SectionHead`; the chromatography column write endpoints have `Equipment.Manage` (see FS-EQP). The laboratory-scope rule is not in the controllers. Each service applies it in its own way: Test Master and workflow steps use `TestConfigurationScope.EnsureCanConfigureAsync` (FS-MDM-010 to FS-MDM-014); specifications use `SpecificationOwnership.EnsureCanEditAsync` (FS-MDM-005 to FS-MDM-007); water and after-cleaning test configurations use `TestCodeOwnership.EnsureCanEditAsync` (FS-MDM-020, FS-MDM-022). Items, organisms, reference lists, EM master data and media configurations make no laboratory-scope check (see the entries). `Sections.ConfigureAll` opens configuration in every section; it does not open GxP records.
**Code:** `backend/MicroLIMS.Application/Services/UserSectionScopeService.cs` — `GetConfigurableSectionIdsAsync`, `ResolveSectionForCreateAsync`; `backend/MicroLIMS.API/Controllers/TestDefinitionMasterDataController.cs` — class and action attributes

### FS-MDM-006
**Satisfies:** URS-MDM-003, URS-MDM-004, URS-MDM-009, URS-MDM-010
**Function:** Specification update. The row is loaded with its stages and `RecordVersion.EnsureCurrent` is called. The scope check is made twice: for the row's current test code and for the test code in the request, so a user cannot move a row into or out of a laboratory by changing the code. The method then overwrites the row in place: the test code, limits, inclusivity, target, tolerance, unit, dilution factor, result basis, grade and the other fields are replaced by the request values (parameter name, display order, limit type, inclusivity flags and the three limit strings are replaced only when sent). The stages are removed and re-created from the request. The method then runs `ApplyCanonicalSpecLimit` and `ValidateAsync`. The old row is not kept as a version and no snapshot is made; the only record of the old values is the automatic audit row (old and new values). No reason for change is asked for. Whether recorded results keep their own copy of the limits was not checked here; the comment in `DeleteSpecificationAsync` says results copy the alert, action and specification values as plain strings at calculation time.

### FS-MDM-008
**Satisfies:** URS-MDM-004
**Function:** Specification validation, called by create and update. Rules by limit type, as coded: Range needs both limits and lower not above upper; NotMoreThan needs an upper limit; NotLessThan needs a lower limit; TargetWithTolerance needs target, tolerance (above zero) and a tolerance mode; Qualitative needs expected text; PresenceAbsence needs an expected state; MultiStage needs at least one stage and every stage needs a label and acceptance text; DissolutionQ needs a lower limit above 0 and not above 100, a label claim above 0 and the label-claim unit "mg"; DisintegrationTime needs an upper limit above 0, the unit "min", and no label claim; WeightVariation needs a dosage form, the unit "mg" and no limits or label claim; CountTiered has no extra rule. A dilution factor is allowed only for CountTiered; a dosage form only for WeightVariation; basis ppm only with an HPLC method analyte. `ApplyCanonicalSpecLimit` rebuilds the specification-limit text from the numeric fields for every limit type except CountTiered, and for those types it blanks the alert and action limit strings and the dilution factor. `ValidateAsync` also requires a parameter name and a test code; normalises the grade (trimmed, at most 20 characters, "BP" and "USP" stored upper-case) and reuses the spelling of an existing grade of the item that matches without regard to case; requires that the test is assigned to the item (`SampleTests`); applies the moisture-basis rule (`NotApplicableTestService.EnsureSpecBasisHasMoistureAsync`); refuses a physicochemical test for the wrong item category area; allows a production stage role only on Finished Product items and never the value Other; and refuses duplicates by analyte and basis, ICP element and basis, related-substance row kind, or parameter name, each within item, test, stage role and grade (grade compared without regard to case). Related-substance rows must be NotMoreThan limits with basis "percent as is", no label claim, and a named impurity that belongs to the test's HPLC method.
**Code:** `backend/MicroLIMS.Application/Services/SpecificationService.cs` — `Validate`, `ValidateAsync`, `ApplyCanonicalSpecLimit`, `BuildCanonicalSpecLimit`, `NormalizeGrade`, `ValidateRelatedSubstanceRowAsync`

### FS-MDM-010
**Satisfies:** URS-MDM-002, URS-MDM-005, URS-MDM-006, URS-MDM-009, URS-MDM-010, URS-MDM-014
**Function:** Test Master, update. The method runs in one database transaction (`UnitOfWork.RunAsync`). Order: load the test with its ICP elements; call `RecordVersion.EnsureCurrent`; refuse the retired types; refuse a code that another test already uses; call `TestConfigurationScope.EnsureCanConfigureAsync` for the test's section (refuses with `UnauthorizedAccessException` when the user is not assigned to it and does not hold `Sections.ConfigureAll`); if a new section is sent, resolve it with the Configure scope rule. Changing a physicochemical area to a narrower one is refused while specifications of the lost area exist for that test. No check is made on whether the test already has test orders or results; the test code can be renamed here and no other table that holds the old code as text (specifications, assigned item tests, test orders) is changed by this method. Any other change is audited only by the automatic capture, without a reason.
**Code:** `backend/MicroLIMS.Application/Services/MasterData/TestDefinitionMasterDataService.cs` — `UpdateTestDefinitionAsync`, `UpdateTestDefinitionCoreAsync`, `ApplyPhyschemAreaAsync`

### FS-MDM-013
**Satisfies:** URS-MDM-002, URS-MDM-007, URS-MDM-009, URS-MDM-010
**Function:** Test workflow steps, create and update. Inputs: step name, step type, target organism, final-step flag, incubation-transfer flag, confirmatory media count (default 1), phenotypic test type or list, step media (product, required flag, order, incubation condition), incubation stages. Audited by automatic capture; no reason is asked for.

### FS-MDM-017
**Satisfies:** URS-MDM-010, URS-MDM-011, URS-MDM-012
**Function:** Workbook load (signed). Inputs: file, file name, password, optional comment (at most 2000 characters; the name at most 260 characters). In one transaction (`UnitOfWork.RunAsync`) the method adds a load record with the file's SHA-256, the user and the UTC time from the injected clock, status Loaded, and saves it. It then calls `IElectronicSignatureService.SignAsync` with the user ID, the password and the meaning "MasterDataChanged"; a wrong password fails here, before any row is touched. Then `MasterDataWorkbookRunner.RunAsync` loads the rows: sheets in load order; unknown sheets are errors; a limit of 5000 new rows; required columns must exist; a row is a duplicate within a sheet or must not already exist with different values (the workbook only adds records; a row already present with the same values counts as unchanged); each new row is created through the existing master-data service for its type inside a savepoint, so a failing row is rolled back alone and all errors are listed. Existence is compared across all sections, not only the user's. If there is any error the whole load is rolled back and no file is stored. Otherwise the file is saved to storage, the load record gets the storage key and a per-sheet summary, and one record per created row is added. Items are created then set inactive; material master entries and reference organisms are created then set inactive. The media product and equipment sheets do not set the new record inactive in the code read. Specifications and specification stages are created through `SpecificationMasterDataService.CreateSpecificationAsync` with the loader's user ID (so the scope check of FS-MDM-005 applies) and are not set inactive. The sheet handlers call `ItemService`, which makes no laboratory-scope check; the test codes of an item row must exist in the Test Master (case-insensitive). The file is stored before the final commit, so a failed commit can leave an orphan file (code comment). The result says whether the load was accepted. Per the code comment on `ImportAsync`, a refused signature attempt stays on record although everything else rolls back. The signature is bound to the load record (entity type MasterDataImport, the load ID); the signed content is built by the signature service, not by the browser.
**Code:** `backend/MicroLIMS.Application/Services/MasterDataWorkbook/MasterDataWorkbookService.cs` — `ImportAsync`; `backend/MicroLIMS.Application/Services/MasterDataWorkbook/MasterDataWorkbookRunner.cs` — `RunAsync`
**Verified by:** reading (not run)
**Conflicts:** CONF-153, CONF-154

### FS-MDM-018
**Satisfies:** URS-MDM-010, URS-MDM-012, URS-MDM-013
**Function:** Workbook verification (second person, signed). Inputs: load ID, password, comment (at most 2000 characters). In one transaction: the load is fetched with its records (not-found if absent); its status must be Loaded; the verifier must not be the user who loaded it. Only those three kinds are activated here; the verification does not touch media products or equipment created by the workbook. The list of loads and the stored file are read by `GetImportsAsync` and `GetFileAsync`, which need `MasterData.Manage` only and make no section check.

### FS-MDM-020
**Satisfies:** URS-MDM-002, URS-MDM-008, URS-MDM-009, URS-MDM-010, URS-MDM-015
**Function:** Water master data. Sampling points: create checks `TestCodeOwnership.EnsureCanEditAsync` for the assigned test codes (a user may assign only tests of sections they configure; `Sections.ConfigureAll` is unrestricted) and applies the frequency rule; update calls `RecordVersion.EnsureCurrent` and applies the ownership check only to test codes added or removed; delete refuses a user who does not own every assigned test code, and refuses while any sample, sample location or sampling configuration uses the point.
