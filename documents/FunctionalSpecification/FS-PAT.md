## Scope and reading notes

- Two code paths record pathogen (presence/absence) results. (1) The per-test-order chain in `PathogenConfirmationRecorder`, reached from `TestWorkflowController` (entries FS-PAT-009 to FS-PAT-012). (2) The per-sample "testing session" in `PathogenSessionService`, reached from `PathogenSessionController` (entries FS-PAT-001 to FS-PAT-008 and FS-PAT-013). They apply different rules in places; see CONF-016.
- The steps, media, number of confirmatory media and incubation windows of a test come from its configured workflow steps. The step types in the code are BrothEnrichment, SelectiveBroth, SelectivePlating, ConfirmatoryPlating and BiochemicalTest. Which organism a test targets is configured by the Section Head (target organism on the step). This document names no organism.
- Nothing was run. None of the methods here checks a record version (`If-Match`). Entries state where a database transaction is used.
- The backend file `PathogenWorkflowEngine.cs` named in `documents/DesignSpecification/BusinessRules.md` was searched for by name and does not exist (see CONF-015).

## Functions

### FS-PAT-001
**Satisfies:** URS-PAT-001
**Function:** All session endpoints need the permission `TestWorkflowExecute`; reset also needs `TestWorkflowSupervise`. Each endpoint first calls `EnsurePathogenSampleAccessAsync`, which looks at the sample's current (not superseded) test orders whose test definition has workflow type Observation, and refuses when any of those orders belongs to a section outside the user's scope (read access: all sections for a holder of `Sections.ViewAll`; write access: member sections only). A sample with no Observation-type orders is not scope-checked at all, and a missing sample passes the check. Test orders of other workflow types on the same sample are not looked at by this check, although the session methods change locations and orders for every test code on the sample. Controller methods turn `WorkflowStepException` into HTTP 400 with the error code and message, and turn any other exception except concurrency and not-found into HTTP 400 with the message. `GetSession` builds the session view on read: locations, assigned tests, shared enrichment state, the result matrix and the list of missing results.
**Code:** `backend/MicroLIMS.API/Controllers/PathogenSessionController.cs` — `GetSession`, `StartSharedTsb`; `backend/MicroLIMS.Application/Services/UserSectionScopeService.cs` — `EnsurePathogenSampleAccessAsync`
**Verified by:** reading (not run)

### FS-PAT-002
**Satisfies:** URS-PAT-002, URS-PAT-003
**Function:** Start the shared enrichment broth for all tests of a sample (endpoint `start-tsb`). Inputs: media lot ID, incubator equipment ID, optional incubation start time. The method runs in one transaction. Rules in order: (1) preparation gate — the sample preparation status must be Ready and, for samples with an item, a preparation record must exist; when not, a `TestStartRefused` audit row and a workflow-history row are written per test order and the call fails with code PreparationNotConfirmed (by reading `UnitOfWork`, these rows are rolled back with the transaction on a relational database; this was not run); (2) the lot must exist and its expiry date must not be before today (UTC date); (3) the incubator must exist and be of type Incubator; (4) each test order of the sample joins when its first shared-enrichment step (found by `TsbDetectionHelper.IsSharedTsbStep`) accepts this lot's media product; a joining test must have a configured window and an in-range incubator (FS-MIC-003) or the whole start is refused naming the test; a test whose enrichment medium does not accept the lot does not join; if no test has an enrichment step, or none accepts the lot, the call fails; (5) the lot must belong to the section of every joining test order. The method does not test that the lot is released for use or that its status is not rejected, out of stock or expired by status. The incubation start time is taken from the request when given, otherwise from the clock; no limit is placed on how far in the past or future the request time may be. Before adding rows, existing incubations of the joining orders whose step name contains "TSB" or "Enrichment" are removed from the database. For each joining test an incubation is added (end equals start plus that test's medium maximum hours), the order is set to Incubating with approval status Pending (set directly, not through `WorkflowStateMachine`), and a workflow-history row is added whose "from" step is written as Running. A `WorkflowStepResult` row marked as shared-session step is added for each joining order for the enrichment step name. The session view is returned.
**Code:** `backend/MicroLIMS.Application/Services/PathogenSessionService.cs` — `StartSharedTsbAsync`, `StartSharedTsbCoreAsync`, `EnsurePreparedAsync`, `ResolveJoiningTestsAsync`
**Verified by:** reading (not run)
**Conflicts:** CONF-013, CONF-014, CONF-018, CONF-026, CONF-028

### FS-PAT-003
**Satisfies:** URS-PAT-004, URS-PAT-005
**Function:** Save primary growth observations per location and test (endpoint `save-primary-observations`). Input: a list of (test code, sample location ID, growth observation, optional selective-medium snapshot text). Observation values are NoGrowth, GrowthNonConforming and GrowthConforming. The whole request is first checked: every test code in it must be in a state where result entry is allowed (see FS-PAT-013) or the call fails with code PrerequisiteNotMet and records nothing. Entries whose test code or location is not on the sample are skipped without error. Each entry upserts the primary observation for (location, test order) — an existing row is overwritten (observation, observer, time) — and sets the location: NoGrowth gives reported result "Not Detected (-)" and status Absent; GrowthConforming gives "Growth Conforming (Presumptive +)" and status PendingConfirmation; GrowthNonConforming gives "Growth Non-Conforming" and status PendingConfirmation. Entered time and user are set on the location. No transaction wrapper is used; one save is made. No check is made of the sample or test order status, so entry is possible while the order is at Ready (see FS-PAT-013). No password or signature is asked for.
**Code:** `backend/MicroLIMS.Application/Services/PathogenSessionService.cs` — `SavePrimaryObservationsAsync`, `UpsertPrimaryObservation`
**Verified by:** reading (not run)
**Conflicts:** CONF-018, CONF-021

### FS-PAT-004
**Satisfies:** URS-PAT-005
**Function:** Choose locations for confirmation and start the confirmation incubation (endpoints `eligible-confirmations` and `start-confirmatory-setup`). A location is eligible when its primary observation is GrowthConforming or GrowthNonConforming. The number of confirmatory media required is read from the test's configured ConfirmatoryPlating step; when the test has no such step the setup is refused with code ConfirmatoryStepNotConfigured. Setup input: test order ID, location IDs, material IDs of the chosen media, optional media lot IDs, incubator ID, optional start time. Checks: the number of chosen materials must equal the configured number; every location must be eligible; the incubator must exist and be an Incubator; every chosen material must belong to the test order's section; every chosen medium must be on the step's permitted list and have a configured window; the incubator must be in range for every chosen medium. When lot IDs are given they are checked for section only. Result: one incubation row is added for the test order (end equals start plus the longest maximum hours of the chosen media; start from the request when given, otherwise the clock, with no bound), the order is set to Incubating directly with a workflow-history row (from-step written as Running). The method does not check that lots are given, released, in date, or that the primary observation incubation has finished; when no lot ID is given the incubation is stored with media ID 0. Only one incubation is created for all chosen locations; the chosen location IDs are validated but not stored on it.
**Code:** `backend/MicroLIMS.Application/Services/PathogenSessionService.cs` — `GetEligibleLocationsForConfirmationAsync`, `StartSharedConfirmatorySetupAsync`, `ResolveChosenConfirmatoryMediaAsync`
**Verified by:** reading (not run)
**Conflicts:** CONF-013, CONF-014

### FS-PAT-005
**Satisfies:** URS-PAT-006
**Function:** Save confirmatory plate readings and decide the location result (endpoint `save-confirmatory-readings`). Input: readings of (primary observation ID, material ID, medium index, growth observation) and an optional biochemical comment. Each reading upserts one confirmatory plate row for (primary observation, material, medium index) — an existing row is overwritten — and stores the expected-appearance text for the target organism configured on the step at that moment. Readings whose primary observation ID is unknown are skipped. After saving, for each primary observation that has at least the required number of plates, `ConfirmationAgreementEvaluator.EvaluateAgreement` is applied to the first required plates ordered by medium index. Rule as coded: if every plate is GrowthConforming the location is Detected ("Detected (+)"); if every plate is NoGrowth or every plate is GrowthNonConforming the location is NotDetected, stored as status Absent ("Not Detected (-)"); any other mix, including NoGrowth with GrowthNonConforming, is Inconclusive ("Inconclusive (Retest)", status Inconclusive). The call throws when the plate count differs from the required count. A comment, when given, is written to the workflow history of each affected order. The method does not check the scope of the sample (the controller does), does not check that the confirmation incubation has finished, and does not check that the primary observations belong to the sample in the URL. No transaction wrapper is used.
**Code:** `backend/MicroLIMS.Application/Services/PathogenSessionService.cs` — `SaveBatchConfirmatoryPlateReadingsAsync`, `ApplyConfirmationAgreement`; `backend/MicroLIMS.Application/Services/ConfirmationAgreementEvaluator.cs` — `EvaluateAgreement`
**Verified by:** reading (not run)
**Conflicts:** CONF-016, CONF-017, CONF-018, CONF-021

### FS-PAT-006
**Satisfies:** URS-PAT-004
**Function:** Save the result matrix (endpoint `save-matrix`) for any test on the sample. Input: cells of (test code, location ID, result type, numeric value, result display text, result code). Every cell's test must allow result entry (FS-PAT-013) or the whole call fails with PrerequisiteNotMet. A Quantitative cell stores the numeric value as CFU and calculated result, stores the reported text as the display text sent by the client (or "{value} CFU" when none), copies the alert, action and specification texts from the location's sampling configuration, and sets the status by `SpecLimitParser.CompareAgainstLimits` (no status when no value is sent). Any other cell is read as Detected when the result code equals the literal "DETECTED" or the display text contains "Detected (+)", otherwise Not Detected; it sets the reported text and status Detected or Absent and upserts a primary observation (GrowthConforming or NoGrowth). The backend does not round the numeric value, does not check it is a whole number or non-negative, and does not build the reported text for a Quantitative cell. No transaction wrapper is used.
**Code:** `backend/MicroLIMS.Application/Services/PathogenSessionService.cs` — `SaveResultMatrixAsync`
**Verified by:** reading (not run)
**Conflicts:** CONF-019, CONF-018, CONF-028, CONF-029

### FS-PAT-007
**Satisfies:** URS-PAT-007
**Function:** Complete the session (endpoint `complete`). Preconditions: the session view lists no missing (location × test) result; no assigned test is in state TSB_INCUBATING or has result entry not allowed. Result: every test order of the sample (including any that are superseded or already approved) is set to step Ready and status ResultEntered directly, with a workflow-history row (from-step written as Running); the sample status is set to UnderReview and its reviewed-at time cleared; a "submitted for review" review event is logged. No `Result` row is written by this method. No transaction wrapper is used and `WorkflowStateMachine` is not used, so its refusal for closed orders does not apply. No check is made of who completes, so the completing user may be the user who entered the results; the review step later applies FS-REV-009.
**Code:** `backend/MicroLIMS.Application/Services/PathogenSessionService.cs` — `CompleteSessionAsync`

### FS-PAT-008
**Satisfies:** URS-PAT-008
**Function:** Reset the session (endpoint `reset`; permission `TestWorkflowSupervise`). Input: optional reason. Refused for a sample with status Voided or Rejected. For any other sample status, including Approved, the method permanently deletes all primary observations, confirmatory plate observations and media selections, workflow step results, pathogen observations, count readings, results and incubations of the sample's test orders; clears the CFU value of each location; sets every test order to Waiting and Pending (directly, not through `WorkflowStateMachine`); adds a workflow-history row per order with the reason; sets the sample back to Received only if it was InTesting or UnderReview; and writes one audit row (`ResetWorkflowSteps`) with the reason. The reason is optional; when blank the text "Analyst requested session workflow reset" is stored. No password or signature is asked for. The reported-result text and status on locations are not cleared.

### FS-PAT-009
**Satisfies:** URS-PAT-009, URS-PAT-010
**Function:** Per-test-order chain, enrichment and selective plating (endpoints `submit-broth`, `start-selective-plating-incubation`, `submit-selective-plating-observation`). Common checks (`LoadOrderAndStepAsync`): the order must not be at Ready, Reviewed or Approved; the step must be in the test's configuration; it must be the first incomplete step; every lower step must be done and have no open incubation. `submit-broth` (BrothEnrichment or SelectiveBroth steps): an open incubation for the step must exist (or a completed one, which only creates the step-result row); the medium's minimum hours must have passed unless a user overrode the minimum; then the incubation is closed with the optional observation text, a step-result row is added if none exists, and for enrichment steps the shared enrichment is propagated to sibling orders. `start-selective-plating-incubation`: sample preparation gate (FS-MIC-011); the step must have at least one configured medium and the first one is used; the lot must be released for use, not out of stock or rejected, from the order's section, and of the permitted product; window configured; incubator in range; start time from the request when given (no bound), otherwise the clock; the incubation is added and the sample and order move to InTesting/Incubating. `submit-selective-plating-observation`: an open incubation must exist and the medium's minimum hours must have passed unless overridden; the incubation closes; a step result is stored with the observation and the expected-appearance text for the step's target organism (refused when no target organism is configured); a pathogen observation row is added. If the observation is GrowthConforming the chain continues. Any other observation (NoGrowth or GrowthNonConforming) ends the workflow with the final result NotDetected: a `Result` row is added, the order goes to Ready through `WorkflowStateMachine`, the result is projected and the sample review hook runs (FS-REV-003). The submit and start methods run in transactions. The lot's expiry date is not checked.
**Code:** `backend/MicroLIMS.Application/Workflows/TestWorkflow/PathogenConfirmationRecorder.cs` — `SubmitBrothCoreAsync`, `StartSelectivePlatingIncubationCoreAsync`, `SubmitSelectivePlatingObservationCoreAsync`, `LoadOrderAndStepAsync`
**Verified by:** reading (not run)
**Conflicts:** CONF-013, CONF-014, CONF-016

### FS-PAT-010
**Satisfies:** URS-PAT-011
**Function:** Per-test-order confirmatory plating (endpoints `submit-confirmatory-setup`, `submit-confirmatory-observations`). Setup: refused when a step result already exists for the step (different codes for "set up and waiting" and "already read out"); at least one medium must be selected; each selected medium must be on the step's permitted list and have a lot and an incubator; the lot must be released, not out of stock or rejected, from the order's section and of the permitted product; the incubator must be in range for the medium. The window is the longest maximum hours of the chosen media, and must end after it starts and last at least the longest minimum hours; the start time is taken from the request with no bound on how far in the past it is. One incubation and one step result with the selections are saved. The number of media chosen is not compared with the step's configured confirmatory media count in this method. Observations: the unread step result must exist; the incubation end time (start plus longest maximum hours) must have passed unless a user overrode the minimum; there must be exactly one observation for each selected medium and no duplicates; each stores the expected-appearance text. The confirmatory result is AllConforming when every observation is GrowthConforming, otherwise Inconclusive; an Inconclusive result adds a workflow-history row "flagged for investigation" and returns the flag InconclusiveResult. The incubation closes. The observation method is not wrapped in a transaction wrapper. No path in this method gives a final result.
**Code:** `backend/MicroLIMS.Application/Workflows/TestWorkflow/PathogenConfirmationRecorder.cs` — `SubmitConfirmatorySetupCoreAsync`, `SubmitConfirmatoryObservationsAsync`
**Verified by:** reading (not run)
**Conflicts:** CONF-013, CONF-014, CONF-016

### FS-PAT-011
**Satisfies:** URS-PAT-012
**Function:** Analyst decision and biochemical step (endpoints `analyst-decision`, `submit-biochemical`). Analyst decision: allowed only when the latest confirmatory result is AllConforming and no decision exists yet (single shot). ProceedToBiochemical writes a workflow-history row and leaves the order open. Any other decision submits the test as Detected without biochemical confirmation: the step result is flagged SkippedBiochemical, a `Result` row with Detected is written, the order goes to Ready, the result is projected, the sample review hook runs, and the response carries the flag BiochemicalNotPerformed. No password, reason or signature is asked for in either branch. Biochemical submission: the result text must not be blank; the nearest preceding selective or confirmatory plating step must have a stored result that allows it (confirmatory: AllConforming or Inconclusive; selective plating: GrowthConforming); a step-result row is saved with the text, optional attachment ID and the analyst's yes/no "organism detected" flag. If the step is the last configured step the final result is Detected when the flag is yes, otherwise NotDetected, and the order is finalised as in FS-PAT-009; a final result is never taken from the free text.
**Code:** `backend/MicroLIMS.Application/Workflows/TestWorkflow/PathogenConfirmationRecorder.cs` — `RecordAnalystDecisionCoreAsync`, `SubmitBiochemicalCoreAsync`, `FinalizeWorkflowAsync`

### FS-PAT-012
**Satisfies:** URS-PAT-012
**Function:** Reviewer decision on a result submitted as Detected without biochemical confirmation (endpoint `results/{workflowStepResultId}/biochemical-decision`; permission `TestWorkflowBiochemicalDecision`). The controller makes the section scope check on the result's test order. The method refuses when `SegregationOfDutiesGuard.DidUserPerformTestAsync` is true for the deciding user (code SegregationOfDutiesViolation). The method runs in one transaction. No password or electronic signature is asked for in either branch.

### FS-PAT-013
**Satisfies:** URS-PAT-004
**Function:** How the session decides that result entry is allowed for a test (view built by `GetSessionAsync`, rule in `WorkflowStateResolver.Resolve`). Closed states first: superseded, voided, cancelled, approved, rejected, or sample on hold for retest allow no entry. A test at Reviewed allows none. A test at Ready ("Result Recorded, Pending Review") allows entry. For a test with a shared enrichment step: no enrichment incubation means not allowed; an unresolved window means not allowed; enrichment still inside its minimum hours means not allowed; after the minimum hours, entry is allowed when no later non-enrichment step is incubating inside its minimum hours and all later steps other than confirmatory and biochemical steps are complete. For other tests: an open count incubation still inside its minimum hours (stage 2 uses the configured stage 2 minimum) does not allow entry; once past it (a user override counts as passed) entry is allowed; a test at Incubating with no open incubation does not allow entry; a test at Running allows entry; any other test, including one at Waiting that has not started an incubation, falls to the default and allows entry. The readiness for enrichment uses the medium's minimum hours, not the end of the window. The shared-enrichment panel also fills two display fields: GPT status is "Passed (GPT Conform)" when the lot is flagged released, otherwise "Pending"; sterility status is the fixed text "Passed" whatever the lot's records say. Steps are found by name in places (names containing "TSB" or "Enrichment").
**Code:** `backend/MicroLIMS.Application/Services/WorkflowStateResolver.cs` — `Resolve`; `backend/MicroLIMS.Application/Services/PathogenSession/SharedTsbStateBuilder.cs` — `Build`
**Verified by:** reading (not run)
**Conflicts:** CONF-010, CONF-018, CONF-020, CONF-028
